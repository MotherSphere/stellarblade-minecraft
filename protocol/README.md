# Shared protocol

The shared directory is private to the local user (0700). Text snapshots are bounded and versioned. Readers validate complete-message footers, identity, timestamps, revisions, dimensions and finite coordinates before using a snapshot. Implementations and shared [fixtures](fixtures/) are authoritative for exact grammars and bounds.

| Product | Producer | Reader | Contract |
|---|---|---|---|
| Terrain | Minecraft | Lua | `SBMC 3 TERRAIN`, fixed anchor, revision, the window following EVE and at most 1024 distinct merged boxes relative to its corner |
| EVE position | Lua | Minecraft | `SBMC 2 EVE`, session, state, acknowledged terrain revision and feet position within ±2048 blocks |
| Native terrain visuals | Minecraft | Lua | Independent visual revision and supported face/texture data |
| Capture request | Minecraft | Lua/native | `SBMC_CAPTURE_SESSION 2`, RUN, SESSION, TIME, SIZE, STATE, END |
| Raw frame | Native | Minecraft | Mapping v1 containing frame-v6 metadata, RGBA8 and R32F depth |
| Control permit | Lua | Native | `SBMC_CONTROL 1`, run/session, generation, sequence and native context |
| Input / acknowledgement | Minecraft / native | Native / Minecraft | `SBMC_INPUT 1`, ordered edges, epochs, sequence and leases |
| Pose request | Minecraft | Lua/native | `SBMC_POSE_REQUEST 1`, RUN, TIME, STATE, END |
| Pose components | Lua | Native/Minecraft | `SBMC_POSE_COMPONENTS 1`, generation, placement and the skeletal mesh components of EVE and her drone |
| Pose | Native | Minecraft | Pose mapping v1, slot format 4, with world, component-space bone and morph-weight floats |
| Combat event | Minecraft | Lua | `SBMC_COMBAT 2`, SESSION, SEQ, TIME, EVENT and attacker yaw, END |
| Lock-on target | Minecraft | Lua | `SBMC_LOCK 1`, SESSION, SEQ, TIME, TARGET position or `none`, END |
| Mob walls | Minecraft | Lua | `SBMC_MOBS 2`, SESSION, SEQ, TIME, COUNT and up to eight MOB boxes, END |
| Session request / answer | Minecraft / Lua | Lua / Minecraft | `SBMC_REQUEST 1`, SESSION, SEQ, TIME, ACTION, END; `SBMC_REQUEST_ACK 1`, SESSION, SEQ, ACTION, RESULT, MESSAGE, END |
| HUD and items | Lua | Minecraft | `SBMC_HUD 1`, SESSION, SEQ, TIME, HEAL, UTIL, AMMO, DASH, USES, END |

Positions use Unreal `(X,Y,Z)` to Minecraft `(X,Z,Y)` with 100 Unreal units per block and the session's anchor transform. Native camera/depth and feet position must match the terrain link; mixing older coordinate bases is unsupported.

## Terrain window

Minecraft replaces [`terrain.txt`](fixtures/terrain.txt) every 4 server ticks: SESSION, SEQ (the revision, raised when the boxes or the window change), TIME in Unix seconds, `WORLD dimension x y z` (the fixed bridge origin), `BOUNDS minX minY minZ maxX maxY maxZ`, `COUNT n` (at most 1024), n distinct `BOX` lines and `END` with SEQ. BOUNDS is the window relative to the origin, within ±2048 blocks: five by three by five world-aligned cells of 8 blocks around EVE's cell, moved by whole cells once her feet are two cells from its centre horizontally, or within 4 blocks of its floor or 6 of its ceiling. Each BOX is relative to the window's minimum corner and rounded to a ten-thousandth of a block, so a full packet fits 64 KiB anywhere in reach; Lua adds the corner back and rounds again, recovering Minecraft's coordinates exactly, and refuses boxes outside the window, empty or duplicate after rounding. Lua names formats 1 and 2 as an older Minecraft mod. Within one session, dimension and origin, a new BOUNDS is a window move, not a new link: Lua spawns the new window's guards, then its missing boxes within 4 ms per native frame, and only then removes the boxes the revision no longer has and the old guards; it acknowledges the revision (`STATE ... ack`) only once that is done, and defers a move while EVE's feet are outside the new window or a new guard would intersect her capsule. Minecraft keeps each window from the first revision that published it until EVE acknowledges a newer one, and applies her position only inside the window of the revision she acknowledges. Once her newest packet is `idle` or `ready`, or 30 seconds old, the window follows the anchor again.

## Raw mapping v1

Minecraft exclusively creates `eve-frames-<RUN>.bin` with mode 0600. RUN and SESSION are separate 32-character lowercase hexadecimal identities. Each run fixes width 1–3840 and height 1–2160. Let `P = width * height`, `stride = align64(4096 + P * 8)`, and `total = 4096 + 3 * stride`. Integers and float planes use little-endian layout.

| Header offset | Field |
|---|---|
| 0 | Eight-byte magic `SBMCFRM1` |
| 8, 12 | Version 1; header size 4096 (u32) |
| 16, 20, 24, 28 | Width, height, slot stride, total bytes (u32) |
| 32, 64 | RUN and SESSION (32 ASCII bytes each) |
| 96 | Consumer PID (u32) |
| 128 | Atomic middle-slot index with dirty bit 4 (u32) |
| 192, 196, 200 | Producer PID, state, error (u32) |
| 208, 216 | Producer Unix milliseconds and completed counter (u64) |
| 256, 264, 272 | Consumer state (u32), Unix milliseconds and accepted counter (u64) |

Reserved bytes are zero. Producer states are 0 unclaimed, 1 ready, 2 released, 3 failed. Consumer states are 1 active, 2 stopped. Producer PID `UINT_MAX` marks a cancelled unclaimed run. Claims and cancellation use the same atomic word.

Initially the producer owns slot 1, consumer slot 2 and middle slot 0. Atomic exchange transfers middle ownership; a published middle sets dirty bit 4. The reader copies its acquired slot before exchanging again. A slot contains counter (u64) at 0, publication Unix milliseconds (u64) at 8, metadata length (u32) at 16, format 1 (u32) at 20, ASCII frame-v6 metadata at 64, RGBA8 at 4096, then P R32F depth values. Metadata is limited to 2048 bytes.

A frame-v6 generation is exactly two registered image jobs, color and depth, in either order; a `MASK depth 0` line records that no coverage job exists. Alpha is 255 where depth is positive and below 65504 (the binary16 capture clear value) and 0 elsewhere. Non-finite or non-positive depth becomes 0. A retired mask job fails the run. No mapped slice escapes the Java reader. Native release acknowledgement is required before deleting an active producer's mapping; an unresolved mapping is retained and never reset for another run.

## Pose stream v1

Minecraft refreshes `eve-pose-request.txt` (`SBMC_POSE_REQUEST 1`, RUN, TIME in Unix milliseconds, STATE `active` or `stopped`, END) at least every second; a request older than three seconds is inactive. While it is active, Lua publishes [`eve-pose-components.0/1`](fixtures/pose-components.txt) a few times per second when the composition changes: RUN, a GENERATION that increases within the run, the entered link's SESSION and `ANCHOR x y z unitsPerBlock` (Unreal) or `none`, `CONTROLLER object class offset pawn pawnClass yawScale pitchScale` (the local player controller, the byte offset of its `ControlRotation` as 8 hex digits, aligned, below 0x4000, its pawn and the pawn's class, and the controller's `InputYawScale` and `InputPitchScale` as decimal floats, finite with magnitude 0.01 to 100) or `none`, COUNT (1–16), then per component (EVE's, then her drone's: the `CH_Drone_BP_C` character of tribe `Drone` nearest to her, its component names prefixed `Drone.`, left out rather than exceeding 16 components or one slot of floats) its object, class and skeletal mesh addresses (16 lowercase hex digits), bone count (0 for leader-pose followers, at most 256), morph count (at most 1024), name, mesh name and leader or `-`, followed by `BONES` (component-space order) and `MORPHS` (`MorphTargets` order) name lines, then `PARAMETERS n` (0–32) and per parameter `PARAMETER index component slot name object class offset element nameIndex floats`: a glow parameter (`Opacity`, `Emissive_Intensity`, `Emissive_Color` and their `_2` pairs) of a `MaterialInstanceDynamic` on that component's material slot, with the byte offset of its `ScalarParameterValues` or `VectorParameterValues` array (8 hex digits, 8-aligned, below 0x4000), the element index (below 1024), the FName comparison index expected at the element (positive) and 1 (scalar) or 4 (vector) floats; then `EFFECTS none` or `EFFECTS children asset template activeByte activeMask niagaraClass particleClass n` (byte offsets of `USceneComponent::AttachChildren`, `UNiagaraComponent::Asset` and `UParticleSystemComponent::Template` as 8 hex digits, 8-aligned, below 0x4000; the byte of `UActorComponent::bIsActive` and its mask as 2 hex digits; both component classes) and per effect asset `EFFECT index asset name`, at most 32. Readers take the newer complete slot of their run.

The adapter reads the listed components on the game thread at the verified gameplay XInput poll, after the previous frame's animation and physics. A component is read only while it is the live, non-pending-kill `GUObjectArray` object at its address with the published class and mesh; otherwise its status is 0. A read component is also marked hidden while Stellar Blade does not draw it: `USceneComponent::bVisible` (byte +0x170, bit 5) clear, `bHiddenInGame` (+0x171, bit 2) set, or its owner (`UActorComponent`'s unreflected pointer at +0xb0), when live, with `AActor::bHidden` (+0x58, bit 5) set; its floats are copied all the same. The controller is checked the same way (class only). Faults are contained. While a table with an anchor is published for an active request, Lua grants the native input permit to RUN and that SESSION, as it does for a continuous capture.

Minecraft exclusively creates `eve-pose-<RUN>.bin` (0600, 200704 bytes): the raw mapping v1 header and ownership protocol with magic `SBMCPOS1`, slot stride 65536 at offset 16, payload capacity 16352 floats at 20, total bytes at 28, RUN at 32 and no SESSION. Offsets 224, 228 and 232 hold the producer's last and maximum read time (u32 microseconds) and total read time (u64). With each slot the producer also writes EVE's gauges: five f32 at 324 (Beta, its maximum, Burst, its maximum, the Burst unlock stat), then state 1 at 320, or state 0 when they cannot be read. They come from Stellar Blade's native player actor (game world global at RVA 0x7032570, actor manager +0xc8, actors +0x28 indexed by the player index +0x3c below the count +0x30, stats as floats at +0x118 + 4 × `ESBActorStatType`: 14, 15, 18, 19, 116), only while its life state (+0x2600) is 1 or 6, each finite within 0–100000 and the gauges within their maximums. Seven u32 at 344 count EVE's evade starts since the adapter loaded: first dodges, double dodges and cut first dodges while Minecraft's lock was not applied, the same while it was (its file fresh and input forwarded), then how many lock-gated evade commands the latest locked frame left changed. The adapter reads them each frame from her command set (player actor +0x530, owned when its +0x178 is the actor): a skill whose row is in her tree makes its node current (+0x70) and stores its start time (f32, +0x78); one whose row is not zeroes that time and keeps the node, and the root comes back with time 0 once the node's combo window ends. A start is a new non-zero time on a node whose command (+0x18) is Evade (24): a double dodge when the node's byte at +0xb0 is clear (a combo child, not a row of her stance's own list), else a first dodge (any Evade row of her stance: air dodge, getups and Evade-command attacks included). A first dodge is cut when the time goes to 0 more than 200 ms (wall clock) before its combo window (node +0xac, seconds after its start) ends. With each slot the producer also writes eight f32 at 452, from the same stat array (`ESBActorStatType` 2, 11, 26, 38, 39, 55, 56, 71): MaxHP, ShieldBlock, PhysicAttackPower, CriticalPercentage, CriticalValueRate, MeleeAttackDamageReductionRate, RangeAttackDamageReductionRate and FinalHPDamageReduceRate, then state 1 at 448, or state 0 when they cannot be read (each must be finite within ±100000, MaxHP and PhysicAttackPower above 0). One u32 at 484 counts EVE's drone shots since the adapter loaded, from the same command set: a start (as for evades) of a node whose command is TPSFire (44) and whose action (+0x30, the row's `CommandActionType`) is RangedFireItem (1) or RangedFireSkill (2); her TPSFire rows with action Skill (0) are the empty gun's misfires and do not count. Then comes the adapter's report, u32 counts since the adapter loaded (wrapping): at 488 the heal count (Stellar Blade HP points healed above the mirrored value, below), at 492 the mirror state (0 off, 1 written this frame, 2 held: mirrored but not written, waiting for Minecraft to acknowledge a heal or for a usable share), at 496 the Stellar Blade HP losses the mirror overwrote, at 500 and 504 the Beta and Burst points the adapter added (after rate, cap and clamp); then the player actor's whole stat array, 131 raw f32 (`ESBActorStatType` 0–130 from +0x118, same chain and life states as the gauges, no value checks) at 512, with state 1 at 508, or state 0 when it cannot be read. Bytes 308–312, 372–448 and from 1036 to the end of the header stay zero. After the claim, Minecraft may write its camera: Unix milliseconds (u64) at 288, Unreal Pitch and Yaw (two f32 as one atomic 64-bit word) at 296 and state 1 at 304. Also only after the claim, Minecraft writes two more atomic 64-bit words: at 280 its health word, the bridged player's health share (f32 health over maximum health, in (0, 1], 0 for none: dead, link not entered or not controlled) then the heal count (u32) whose heals it has applied; at 312 its gains word, Beta then Burst base points (u32 each), its cumulative totals since its start, wrapping. The adapter reads them only with a camera it would use (state 1, time within 200 ms, finite angles in range) while forwarded input belongs to the same RUN, and writes only aligned f32 stores into the player actor's stat array (the gauges' chain and life states). Gains: each frame with those words it takes each total's u32 step since the totals it last saw; a first sighting or a step above 1000 adopts the totals without granting, and the totals are adopted before the write, so a step lands once. A frame whose words are stale grants nothing and keeps the totals, so their step lands with the next fresh words; once forwarded input leaves the RUN or the stream stops, the totals are forgotten. A step of `p` points goes into Beta (stat 14) and, while `int(stat 116) > 0`, Burst (18) as Stellar Blade's `FSBActor::AddStat` adds a hit's: with the rate (stat 64 for Beta, 111 for Burst, finite within ±100000) at most 0.4 or 0.75 and `m = |trunc(rate × 1000)|`, the gain is `p` plus `ceil(trunc(m × p / 100) / 10)` with the rate's sign (never below 0), and `value = int(value + gain)`, 0 below 1, at most `int(max)`; nothing is written unless the gauges read as above. Health: Stellar Blade HP (stat 1) carries Minecraft's share of MaxHP (stat 2): MaxHP at a share of 1, else `floor(share × MaxHP)` within `ceil(MaxHP / 4)` and `MaxHP − max(1, ceil(MaxHP / 1000))` (at least the quarter), so it is never 0 and stays below full for Stellar Blade's per-mille "HP below maximum" heal condition; HP must be finite within 0–MaxHP and MaxHP within 1–100000. While mirrored, HP read more than 0.5 above the adapter's last written or seen value adds its rounded rise to the heal count, also while the share is stale; a drop below it counts one loss and is overwritten. The adapter writes only with a usable share (fresh, finite, in (0, 1]) and, after its first write, only once the acknowledged count equals its heal count, so a stale share never erases a heal Minecraft has not applied; Minecraft heals `points × maxHealth / MaxHP` and answers with its new share and the count. After 1 s without a usable share (stream stopped, Minecraft dead, link left, Stellar Blade paused or in a cutscene, Minecraft closed) the adapter writes back the HP read before its first write, at least 1, and stops; another player actor drops the record without a write. While no player actor is spawned the record waits, and her HP on her return is a new base, not a heal. While forwarded input belongs to the same RUN, the adapter turns the game's camera toward a look no older than 200 ms, with finite angles and pitch within ±90 degrees. Yaw goes through the pawn's `AddControllerYawInput` (the game's own look input path, divided by the published scale): each frame Minecraft's motion since the previous frame plus 15 % of the remaining gap to `ControlRotation`, at most 45 degrees. Pitch goes to the game's camera dolly, which carries its camera pitch (`ControlRotation`'s pitch does not track it), while the arm's next pitch follows the dolly's alpha alone: the pawn's `CameraBoom` (+0x5c0) is a live object whose virtual table is `USBSpringArmComponent`'s (RVA 0x5ce42a0) and whose owner (+0xb0) is the pawn; it uses the dolly (`bUseCameraDolly`, +0x2f4) with a `CameraDollyTrackData` (+0x2f8), is in dolly mode (`bLastUseCharacterControllerRot`, +0x370, clear), is not easing its rotation after a mode change (`RemainBlendCamera`, +0x374, at most 0), has no rotation lag (`bEnableCameraRotationLag`, bit 6 of +0x284), is on its default spline (`CurrentDollyMode`, +0x3e0, −1) and blends none (`DollyBlends` count, +0x3d8, 0); the pawn is neither aiming (`bTPSMode`, +0x1528) nor fishing (`FishingModeType`, +0x1690), and its slope camera does not set the alpha (it does while, in `MovementCheckInfo` at +0x1770, `CameraSlopeMoveType` +0x3ec and `bRunCameraSlopeMoveAlpha` +0x3ed are set and `CurrentCameraSlopeMoveRunningTime` +0x3f4 exceeds `CameraSlopeRunTimeFromStart` +0x3fc). Then the adapter adds 1/300 per degree from the arm's last pitch (`PreviousDesiredRot.Pitch`, +0x2c0, taken within ±180) to Minecraft's to `CameraDollyAlpha` (+0x2f0, kept within 0–1), ends the game's dolly blend (+0x3c0..+0x3c7 = 0, +0x3c8 = −1) and sends no pitch input; when a write moved the alpha by more than 0.0001 and the next frame finds the same alpha and the same arm pitch (the arm has not updated: the game paused or hitching), it writes nothing until the arm updates, still with no pitch input. Otherwise Minecraft's pitch motion goes through `AddControllerPitchInput` (divided by the published scale, at most 45 degrees). Minecraft writes yaw within one turn. After 60 consecutive frames with a yaw gap above 30 degrees the adapter stops adding look input until the gap closes; it still sets the dolly meanwhile. The pawn must be the live object of its published class for both; for look input its virtual table and both functions must also lie inside the game image. A slot holds counter (u64) at 0, publication Unix milliseconds (u64) at 8, generation (u64) at 16, format 4 at 24 (Minecraft refuses any other; 4 adds the adapter's report at 488–1036 and Minecraft's words at 280 and 312 to format 3's dolly refusal at 56, its header shot count at 484 and format 2's hidden bit), component count at 28, payload floats at 32, controller status at 36 (bit 0 rotation read, bit 1 camera turned toward Minecraft's this frame, bit 2 camera dolly set from Minecraft's pitch this frame, bit 3 this run owned forwarded input this frame: Stellar Blade granted it, so it was neither paused nor in a cutscene) with its Pitch, Yaw and Roll (f32 degrees, read before this frame's turn) at 40 and, with bit 2, the camera's Unreal pitch (f32 degrees, read before the dolly was set) at 52, else zero, then why the dolly was left to pitch input that frame at 56 (u32: 0 when not tried or set; 1 no camera boom, 2 dolly unused or without a track, 3 arm following the controller, 4 easing after a mode change, 5 rotation lag, 6 another spline or a spline blend, 7 TPS aim, 8 fishing, 9 slope camera, 10 unreadable alpha or arm pitch; never with bit 2), one status word per component at 64 (bit 0 world, 1 bones, 2 morphs, 3 hidden) and the payload at 128: per component its world transform, its bone transforms in component space, then its morph weights; after the last component, each parameter's floats (zeros unless the instance is live with its class and the element still carries the name; elements are 36-byte scalar or 48-byte vector parameter values, value at +16); then, with effects, 8 records of 11 floats: the index of an active effect's asset (-1 for none) and its component's world transform, for live Niagara or Cascade components of those classes attached directly to a live listed component, active, not hidden (as components are) and playing a listed asset. It drops a pose whose first drawn component (EVE's body) lacks its world or bones; any other component without its data or its leader's bones, or hidden, is left out of that pose's drawing, and drawn again once two consecutive poses carry it. A transform is 10 floats: quaternion xyzw, translation xyz, scale xyz, Unreal space. Minecraft decodes a slot only with the table of the same generation.

## Combat events

On each damage to the bridged player from an attacker or projectile, Minecraft replaces [`eve-combat.txt`](fixtures/combat-event.txt): SESSION (the terrain link's), SEQ (increasing within the session, repeated by `END`), TIME in Unix milliseconds, then `EVENT kind yaw` with kind `perfect_dodge`, `perfect_parry`, `parry`, `guard`, `guard_strong` (a guarded attack of at least 8 damage), `hit` or `hit_strong` (a landed attack of at least 8 damage; both strong forms count the damage before EVE's reductions) and the Unreal world yaw in degrees (one decimal, within ±180) from EVE toward the attack's origin, or `none`. A plain dodge publishes nothing. Lua reads it each native frame and acts once per SEQ, only for the entered link's session and within 2.5 seconds of TIME: a perfect dodge plays EVE's `CH_P_EVE_01/Skill/P_Eve_Sword_Normal_JustEvade1` Show through her `SBShowActorInterface.PlaySingleShow`, toward a point 3 m along the yaw, with its full-body key's `bStopAtMove` lifted until the key has started (restored 0.2 s later, retried every frame), since the game's skill blocks movement during it and a lone Show does not; if no new evade effect is on her body mesh 0.2 s later, Lua sets Stellar Blade's global time dilation to 0.3 for half a second of real time (unless the game already runs dilated) and plays the evade Niagara systems instead; a perfect parry plays the two Shows Stellar Blade plays on EVE at a just parry, her own result `CH_P_EVE_01/Skill/P_Eve_Sword_Normal_Guard1_JustParry` and the attacker's `Result/Result_JustParry_FX` (`FX_Parry_Just`), and the bare parry Niagara system only if the latter fails; a parry plays `Result/Result_Parry_Back`; a guard plays `Result/Result_Guard_Back` (`guard_strong`: `Result/Result_Guard_Back_Strong`) with the body key `SBShowAnimKey_0`'s `bCheckHitLevel` lifted in memory for the call, which reads it while building the Show, and restored right after it (retried every frame if that fails); a hit with a yaw makes EVE react, at most every 0.6 seconds and one at a time, through the stock `Hit/Result_Hit_Stand_LightAttack` Show (`hit_strong`: `Hit/Result_Hit_Stand_StrongAttack`, or the light one if it cannot be loaded) by one of three variants (`SBBlueprintLibrary.PlaySBShowToPlayerCharacter`; `PlaySingleShow` with `bCheckHitLevel` lifted in memory on the full-body key Stellar Blade picks for the attack's angle, `SBShowAnimKey_2` within 45 degrees of EVE's facing for the light Show and 50 for the strong one, else `SBShowAnimKey_1`; `PlaySingleShow` with `AdditivePlay` counted into EVE's transient `ShowKeyTagMap`), each undone 1.1 s later and retried until it is; variants take turns, whatever the strength, until one shows a custom-animation alpha from none before, which is kept for both, and stop after 12 counted tries without one (a try while EVE already animates or moves is not counted). The perfect-dodge Show applies its Effect keys as in the game (invulnerability while it plays, Burst gauge, the just-evade counter flag) and the just-parry Show its movement block; a Show's SkillResult key has no effect, and no Show grants a parry's Beta: the adapter adds it from Minecraft's verdicts through the pose stream. The other Shows have no Effect key. Version 1 events are refused. Leaving the link restores time at once; a failed restore is retried every frame. Stopping the bridge deletes the file.

## Lock-on target

While Minecraft's lock-on holds a target, it replaces [`eve-lock.txt`](fixtures/lock.txt) every 50 ms: SESSION, SEQ (increasing, repeated by `END`), TIME in Unix milliseconds and `TARGET x y z`, the target's centre in blocks relative to the bridge origin (Minecraft axes, three decimals, within ±4096), or `TARGET none` once released. Lua takes a newer SEQ of the entered link's session (a first one only within 2.5 seconds of TIME) and keeps the lock for 0.6 seconds after the newest: it spawns a hidden, collisionless, tickless bare `SBCharacter` with an enemy tribe of EVE's (`SupplyNPC` for `PC`), keeps it at the target's Unreal position (anchor + (x, z, y) × scale), sets EVE's `LockOnCharacter` and `bLockOn` with Stellar Blade's lock-on camera off (`bLockOnCameraEnable`) and clears her off-screen timer each frame, so Stellar Blade's own lock-on faces and strafes her, and draws her sword with Stellar Blade's own draw and unfold Shows (the unfold and fold Shows of the `EquipmentTable` row her `EquipmentDataList` names at `EquipmentType_Weapon` (the list follows `ESBEquipmentType`), `LightSword1`'s `Weapon/Eve/NonPonyTail/*_NonTail` copies while her `bHidePonyTail` is set, as the game picks them, and `LightSword1`'s own for an unknown row or a Show that does not play), checked every second while the game is not in battle and does not force it folded (a draw that did not stick is retried with the draw's attach event sent at once, five tries in a row at most) and sheathed once on release if Lua drew it; a lock the game drops is engaged again at once, then at most every 0.25 s while the game refuses it; spawn, follow and engage errors together stop new locks after three. Release, staleness, link loss, F11 or an error releases through the game (target unavailable), restores the camera flag and destroys the proxy, retried every frame until done. The native adapter reads the same file: while it names a target for the session Lua's component table links, with a TIME at most 0.6 s old, and input is forwarded, EVE's lock-gated evade commands take Stellar Blade's lock-on rows (side steps) instead of the plain ones, since the game's own lock target stays empty; each changed command flag is restored on release, staleness or the end of forwarding (one out of her command tree at that moment once it is back). Under the same condition, while EVE is in battle mode (player actor byte +0xB58 is 1, as after an attack), it writes the turn clock's time (the turn manager at the global RVA 0x7032560, checked by its virtual table RVA 0x5bf9120, f32 seconds at +0xc) to her battle-stance stamp (+0x558) when that time is finite and newer, as Stellar Blade's actor update does while its own lock target holds battle mode; it writes nothing else, and once it stops Stellar Blade ends battle mode and sheathes her `BattleStanceCancelTime` (3 s) after the last stamp. Stopping the bridge deletes the file.

## Mob walls

While EVE's position is applied, Minecraft replaces [`eve-mobs.txt`](fixtures/mobs.txt) each server tick: SESSION, SEQ (increasing, repeated by `END`), TIME in Unix milliseconds, `COUNT n` (0 to 8), then n lines `MOB minX minY minZ maxX maxY maxZ`: the nearest living entities that EVE's body shoves and that intersect the terrain window, clipped to it, relative to the bridge origin in blocks (Minecraft axes, three decimals, within ±2048, every side at least 0.01). An empty list is written once, then nothing until an entity is back. Lua takes a newer SEQ of the entered link's session (a first one only within 2.5 seconds of TIME) and keeps the list for 0.6 seconds after the newest: one TriggerBox per box at its Unreal position (anchor + (x, z, y) × scale), WorldDynamic, ignoring every channel except the object type of EVE's capsule, which it blocks, query-only, without overlap events or character step-up. A box that would intersect EVE's capsule is placed without collision until she has left it, and every box is without collision while Stellar Blade lets her pass through characters (`bIgnoreCharacterCollision`, during her evades); unused boxes stay parked without collision. A box is owned before its setup, and a move or collision mode that does not take is an error. Walls are WorldDynamic objects, so a Stellar Blade query by object type (rather than by channel) may still find them. Staleness, link loss, F11 or an error destroys every box, retried every frame until done; three spawn or placement errors stop new walls. Stopping the bridge deletes the file.

## Session requests

`/stellar import`, `/stellar enter` and `/stellar return` replace [`eve-request.txt`](fixtures/request.txt): SESSION (the terrain link's), SEQ (increasing within the session, repeated by `END`), TIME in Unix milliseconds and `ACTION import`, `enter` or `return`. Minecraft sends one at a time, while a bridge session is active and only for its local owner. Lua checks the file on its 200 ms bridge timer and takes a request once: within 2.5 seconds of TIME, and with a newer SEQ when it comes from the session of the last request it took. `import` needs the session `terrain.txt` names, and no linked session of another; `enter` needs a current link (imported or entered) of the same session; `return` runs unless another session is linked, so a failed return can be retried like F11. A request that passes runs the same action as F5 (`sbmc mirror`), F8 (`sbmc enter`) or F11 (`sbmc restore`) on the game thread, with the same checks, log lines and cleanup; one that does not is refused without running. Lua answers every request it takes in [`eve-request-ack.txt`](fixtures/request-ack.txt) (written beside it, then renamed into place after removing the previous answer; Minecraft takes a missing answer as none yet): SESSION, SEQ and ACTION of the request, `RESULT ok`, `failed` or `refused`, `MESSAGE` and the action's message as one line of 1 to 400 printable ASCII characters (others become `?`, an empty one `-`), then `END` with the SEQ. Minecraft shows the answer whose SESSION, SEQ and ACTION match its pending request in chat; after 5 seconds without one it reports no answer and accepts the next request, since Lua's whole-second wall clock cannot take a request more than 3.5 seconds after its TIME. Stopping the bridge deletes both files.

## HUD and items

While a link is entered, Lua publishes [`eve-hud.0` and `eve-hud.1`](fixtures/hud.txt) on its 200 ms bridge timer when the content changes and at least every wall second, written as `eve-hud.tmp` and renamed into slot SEQ % 2 after removing it: SESSION (the entered link's), SEQ (increasing within the Lua lifetime, repeated by `END`), TIME in Unix milliseconds of Lua's whole-second clock, then `HEAL kind count max usable`, `UTIL kind count cooldown usable`, `AMMO alias count cooldown` and `DASH cooldown`, each `none` when absent, and `USES shock pulse mine sonic`. A kind is `tumbler`, `potion`, `lingering`, `field`, `shock`, `pulse`, `mine`, `sonic`, `pump` or `other`; counts are integers 0–9999 (max is the heal slot's `RecoveryPotionMaxCount`, 0 when not shown), cooldowns 0–1 with two decimals, usable 0 or 1, an alias 1 to 64 of `[A-Za-z0-9_]`, uses 0–2147483647. The values are the reflected Blueprint variables Stellar Blade's HUD logic writes into its own widgets: the `WB_MainHUD_ItemSlot_C` instances `WB_MainHUD_HealItem` and `WB_MainHUD_UtilItem` (`ItemCount`, `RecoveryPotionMaxCount`, `CoolTimePercent`, `SlotUseAllow`, and the kind from `Image_Item_Thumb`'s brush texture, `ItemTable.Asset2D`: `Icon_PotionR` tumbler, `Icon_Potion` potion, `Icon_PotionSmall` lingering, `HealGrenade` field, `Grenade` shock, `PluseGrenade` pulse, `TrapGrenade` mine, `FlashGrenade` sonic, `WbPump` pump, any other texture other; a slot without a texture or a readable count is none), EVE's `SBCharacter.CurrentBulletItemAlias` with the `WB_Tps_Bullet2_Slot_C` of that `ItemAlias` (`ItemCount`, `CooltimePercent`), and `WB_MainHUD_Dash_Slot_C.CoolTimeProgress`. Lua keeps the widgets while they are valid; since `FindAllOf` walks every object on the game thread, a missing one is looked for again 2 seconds later, then after twice as long up to 30 seconds (2 seconds again once a search finds one), and at once when a found one goes. A util count that drops while the kind stays the same adds the drop to that kind's use counter (shock, pulse, mine and sonic); a rise (a refill) or another kind (a selection) adds nothing, so a last unit whose slot at once shows another item is not counted.

Minecraft reads both slots each client tick while EVE replaces the player, takes the newer SEQ of the applied link's session and uses it within 2.5 seconds of TIME; a missing or stale file only hides the slots. A use counter step of 1 to 3 is that many new uses (a first sighting, a decrease after a Lua reload or a larger step converts nothing), each applied on the server thread while the bridge overrides the player, to every entity EVE may strike within 3.25 blocks of the player (Stellar Blade's 325 cm): Shock knocks it back and adds Slowness VII and Weakness X for 1.5 seconds; Sonic knocks it back and adds Slowness II and Weakness II for 5 seconds; Pulse knocks it back, removes Absorption and Resistance and deals 12 % of its maximum health as the player's indirect magic; a Smart Mine is placed half a block ahead of the player (three at most, the oldest dropped, gone after a minute or with the override), arms when a monster comes within 2 blocks and 10 ticks later strikes as a strong blade strike, with knockback. Nothing damages blocks or the player. Heal-slot items and the Biotic Field need no conversion: Stellar Blade heals EVE's mirrored HP and Minecraft takes the heal from the pose stream.

## Text publication and legacy captures

Java publishes text with atomic replacement. Lua uses alternating slots where Windows cannot rename over an existing destination. Control permits retire the old slot under a unique owned name before publishing; cleanup failure retains ownership for retry. A missing/stale permit neutralizes input.

Frame-v1 uses PNG color; v2 uses BMP color with PNG mask and HDR depth. Frame-v3 describes a pending asynchronous still and v4 the encoded continuous compatibility path. Frame-v5 described three-job raw payloads and is no longer accepted; v6 replaces it. Pending encoded output requires observed file closure and content validation; metadata alone is insufficient. The active `/stellarview play` and `/stellarview livehd` path uses v6.

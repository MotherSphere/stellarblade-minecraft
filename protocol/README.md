# Shared protocol

The shared directory is private to the local user: owner-only, mode 0700 and files 0600 on Linux, the user profile's inherited ACL on Windows (where it must be a local NTFS folder). Text snapshots are bounded and versioned. Readers validate complete-message footers, identity, timestamps, revisions, dimensions and finite coordinates before using a snapshot. Implementations and shared [fixtures](fixtures/) are authoritative for exact grammars and bounds.

| Product | Producer | Reader | Contract |
|---|---|---|---|
| Terrain | Minecraft | Lua | `SBMC 3 TERRAIN`, fixed anchor, revision, the window following EVE and at most 1024 distinct merged boxes relative to its corner |
| EVE position | Lua | Minecraft | `SBMC 2 EVE`, session, state, acknowledged terrain revision and feet position within ±2048 blocks |
| Native terrain visuals | Minecraft | Lua | Independent visual revision and supported face/texture data |
| Capture request | Minecraft | Lua/native | `SBMC_CAPTURE_SESSION 2`, RUN, SESSION, TIME, SIZE, STATE, END |
| Raw frame | Native | Minecraft | Mapping v1 containing frame-v6 metadata, RGBA8 and R32F depth |
| Control permit | Lua | Native | `SBMC_CONTROL 1`, run/session, generation, sequence and native context |
| Input / acknowledgement | Minecraft / native | Native / Minecraft | `SBMC_INPUT 1`, ordered edges (button masks: XInput's, then LT 0x10000, RT 0x20000 and the walk key 0x40000), epochs, sequence and leases |
| XInput callers | Native | Minecraft | [`SBMC_XINPUT_CALLS 1`](#xinput-callers), TIME, GAMEPLAY and OTHER counts and rates, END |
| Pose request | Minecraft | Lua/native | `SBMC_POSE_REQUEST 1`, RUN, TIME, STATE, END |

Positions use Unreal `(X,Y,Z)` to Minecraft `(X,Z,Y)` with 100 Unreal units per block and the session's anchor transform. Native camera/depth and feet position must match the terrain link; mixing older coordinate bases is unsupported.

## Terrain window

Minecraft replaces [`terrain.txt`](fixtures/terrain.txt) every 4 client ticks, with each new revision at once: SESSION, SEQ (the revision, raised when the boxes or the window change), TIME in Unix seconds, `WORLD dimension x y z` (the fixed bridge origin), `BOUNDS minX minY minZ maxX maxY maxZ`, `COUNT n` (at most 1024), n distinct `BOX` lines and `END` with SEQ. BOUNDS is the window relative to the origin, within ±2048 blocks: five by three by five world-aligned cells of 8 blocks around EVE's cell, moved by whole cells once her feet are two cells from its centre horizontally, or within 4 blocks of its floor or 6 of its ceiling. Each BOX is relative to the window's minimum corner and rounded to a ten-thousandth of a block, so a full packet fits 64 KiB anywhere in reach; Lua adds the corner back and rounds again, recovering Minecraft's coordinates exactly, and refuses boxes outside the window, empty or duplicate after rounding. Lua names formats 1 and 2 as an older Minecraft mod. Within one session, dimension and origin, a new BOUNDS is a window move, not a new link: Lua spawns the new window's guards, then its missing boxes within 4 ms per native frame, and only then removes the boxes the revision no longer has and the old guards; it acknowledges the revision (`STATE ... ack`) only once that is done, and defers a move while EVE's feet are outside the new window or a new guard would intersect her capsule. Minecraft keeps each window from the first revision that published it until EVE acknowledges a newer one, and applies her position only inside the window of the revision she acknowledges. Once her newest packet is `idle` or `ready`, or 30 seconds old, the window follows the anchor again.

## Raw mapping v1

Minecraft exclusively creates `eve-frames-<RUN>.bin` (owner-only: 0600 on Linux; capture mode is Linux-only). RUN and SESSION are separate 32-character lowercase hexadecimal identities. Each run fixes width 1–3840 and height 1–2160. Let `P = width * height`, `stride = align64(4096 + P * 8)`, and `total = 4096 + 3 * stride`. Integers and float planes use little-endian layout.

| Header offset | Field |
|---|---|
| 0 | Eight-byte magic `SBMCFRM1` |
| 8, 12 | Version 1; header size 4096 (u32) |
| 16, 20, 24, 28 | Width, height, slot stride, total bytes (u32) |
| 32, 64 | RUN and SESSION (32 ASCII bytes each) |
| 96 | Consumer PID (u32) |
| 128 | Atomic middle-slot index with dirty bit 4 (u32) |
| 192, 196, 200 | Producer PID, state, error (u32) |
| 208, 216 | Producer Unix milliseconds and completed counter (u64) |
| 256, 264, 272 | Consumer state (u32), Unix milliseconds and accepted counter (u64) |

Reserved bytes are zero. Producer states are 0 unclaimed, 1 ready, 2 released, 3 failed. Consumer states are 1 active, 2 stopped. Producer PID `UINT_MAX` marks a cancelled unclaimed run. Claims and cancellation use the same atomic word.

Initially the producer owns slot 1, consumer slot 2 and middle slot 0. Atomic exchange transfers middle ownership; a published middle sets dirty bit 4. The reader copies its acquired slot before exchanging again. A slot contains counter (u64) at 0, publication Unix milliseconds (u64) at 8, metadata length (u32) at 16, format 1 (u32) at 20, ASCII frame-v6 metadata at 64, RGBA8 at 4096, then P R32F depth values. Metadata is limited to 2048 bytes.

A frame-v6 generation is exactly two registered image jobs, color and depth, in either order; a `MASK depth 0` line records that no coverage job exists. Alpha is 255 where depth is positive and below 65504 (the binary16 capture clear value) and 0 elsewhere. Non-finite or non-positive depth becomes 0. A retired mask job fails the run. No mapped slice escapes the Java reader. Native release acknowledgement is required before deleting an active producer's mapping; an unresolved mapping is retained and never reset for another run. Windows deletes no file while a view of it remains: a deletion refused because the released producer has not unmapped yet is retried later.

## Pose stream v1

Minecraft refreshes `eve-pose-request.txt` (`SBMC_POSE_REQUEST 1`, RUN, TIME in Unix milliseconds, STATE `active` or `stopped`, END) at least every second, from a daemon thread as well as the render thread so a render thread busy for up to 15 seconds cannot let it lapse (Minecraft then restarts its own monotonic lease on the native heartbeat instead of blaming the producer for the stall); a request older than three seconds is inactive. While it is active, Lua publishes [`eve-pose-components.0/1`](fixtures/pose-components.txt) a few times per second when the composition changes: RUN, a GENERATION that increases within the run, the entered link's SESSION and `ANCHOR x y z unitsPerBlock` (Unreal) or `none`, `CONTROLLER object class offset pawn pawnClass yawScale pitchScale` (the local player controller, the byte offset of its `ControlRotation` as 8 hex digits, aligned, below 0x4000, its pawn and the pawn's class, and the controller's `InputYawScale` and `InputPitchScale` as decimal floats, finite with magnitude 0.01 to 100) or `none`, COUNT (1–16), then per component (EVE's, then her drone's: the `CH_Drone_BP_C` character of tribe `Drone` nearest to her, its component names prefixed `Drone.`, left out rather than exceeding 16 components or the table's floats in a slot: 16352, or 13567 beside the ponytail's cloth of up to 17309 particles) its object, class and skeletal mesh addresses (16 lowercase hex digits), bone count (0 for leader-pose followers, at most 512), morph count (at most 1024), name, mesh name and leader or `-`, followed by `BONES` (component-space order) and `MORPHS` (`MorphTargets` order) name lines, then `PARAMETERS n` (0–32) and per parameter `PARAMETER index component slot name object class offset element nameIndex floats`: a glow parameter (`Opacity`, `Emissive_Intensity`, `Emissive_Color` and their `_2` pairs) of a `MaterialInstanceDynamic` on that component's material slot, with the byte offset of its `ScalarParameterValues` or `VectorParameterValues` array (8 hex digits, 8-aligned, below 0x4000), the element index (below 1024), the FName comparison index expected at the element (positive) and 1 (scalar) or 4 (vector) floats; then `EFFECTS none` or `EFFECTS children asset template activeByte activeMask niagaraClass particleClass n` (byte offsets of `USceneComponent::AttachChildren`, `UNiagaraComponent::Asset` and `UParticleSystemComponent::Template` as 8 hex digits, 8-aligned, below 0x4000; the byte of `UActorComponent::bIsActive` and its mask as 2 hex digits; both component classes) and per effect asset `EFFECT index asset name`, at most 32. Then `CLOTH index` (1-based, the component named `SBPonytail` among EVE's own, not her drone's) or `CLOTH none`: the component whose finished cloth the adapter streams. Readers take the newer complete slot of their run.

The adapter reads the listed components on the game thread at the verified gameplay XInput poll, after the previous frame's animation and physics. A component is read only while it is the live, non-pending-kill `GUObjectArray` object at its address with the published class and mesh; otherwise its status is 0. A read component is also marked hidden while Stellar Blade does not draw it: `USceneComponent::bVisible` (byte +0x170, bit 5) clear, `bHiddenInGame` (+0x171, bit 2) set, or its owner (`UActorComponent`'s unreflected pointer at +0xb0), when live, with `AActor::bHidden` (+0x58, bit 5) set; its floats are copied all the same. The controller is checked the same way (class only). Faults are contained. While a table with an anchor is published for an active request, Lua grants the native input permit to RUN and that SESSION, as it does for a continuous capture.

Minecraft exclusively creates `eve-pose-<RUN>.bin` (owner-only, 790528 bytes; on Windows without following a reparse point and sharing read, write and delete, which the adapter's open also shares): the raw mapping v1 header and ownership protocol with magic `SBMCPOS1`, slot stride 262144 at offset 16, payload capacity 65504 floats at 20, total bytes at 28, RUN at 32 and no SESSION. Offsets 224, 228 and 232 hold the producer's last and maximum read time (u32 microseconds, including the copy into the slot) and total read time (u64). With each slot the producer also writes EVE's gauges: five f32 at 324 (Beta, its maximum, Burst, its maximum, the Burst unlock stat), then state 1 at 320, or state 0 when they cannot be read. They come from Stellar Blade's native player actor (game world global at RVA 0x7032570, actor manager +0xc8, actors +0x28 indexed by the player index +0x3c below the count +0x30, stats as floats at +0x118 + 4 × `ESBActorStatType`: 14, 15, 18, 19, 116), only while its life state (+0x2600) is 1 or 6, each finite within 0–100000 and the gauges within their maximums. Eight u32 at 344 count EVE's evade starts since the adapter loaded: first dodges, double dodges and cut first dodges while Minecraft's lock was not applied, the same while it was (its file fresh and input forwarded), then how many lock-gated evade commands the latest locked frame left changed and how many of the seven lock evade rows (see [Lock-on target](#lock-on-target)) the latest lock start left holding 0. The adapter reads them each frame from her command set (player actor +0x530, owned when its +0x178 is the actor): a skill whose row is in her tree makes its node current (+0x70) and stores its start time (f32, +0x78); one whose row is not zeroes that time and keeps the node, and the root comes back with time 0 once the node's combo window ends. A start is a new non-zero time on a node whose command (+0x18) is Evade (24): a double dodge when the node's byte at +0xb0 is clear (a combo child, not a row of her stance's own list), else a first dodge (any Evade row of her stance: air dodge, getups and Evade-command attacks included). A first dodge is cut when the time goes to 0 more than 200 ms (wall clock) before its combo window (node +0xac, seconds after its start) ends. With each slot the producer also writes eight f32 at 452, from the same stat array (`ESBActorStatType` 2, 11, 26, 38, 39, 55, 56, 71): MaxHP, ShieldBlock, PhysicAttackPower, CriticalPercentage, CriticalValueRate, MeleeAttackDamageReductionRate, RangeAttackDamageReductionRate and FinalHPDamageReduceRate, then state 1 at 448, or state 0 when they cannot be read (each must be finite within ±100000, MaxHP and PhysicAttackPower above 0). One u32 at 484 counts EVE's drone shots since the adapter loaded, from the same command set: a start (as for evades) of a node whose command is TPSFire (44) and whose action (+0x30, the row's `CommandActionType`) is RangedFireItem (1) or RangedFireSkill (2); her TPSFire rows with action Skill (0) are the empty gun's misfires and do not count. Then comes the adapter's report, u32 counts since the adapter loaded (wrapping): at 488 the heal count (Stellar Blade HP points healed above the mirrored value, below), at 492 the mirror state (0 off, 1 written this frame, 2 held: mirrored but not written, waiting for Minecraft to acknowledge a heal or for a usable share), at 496 the Stellar Blade HP losses the mirror overwrote, at 500 and 504 the Beta and Burst points the adapter added (after rate, cap and clamp); then the player actor's whole stat array, 131 raw f32 (`ESBActorStatType` 0–130 from +0x118, same chain and life states as the gauges, no value checks) at 512, with state 1 at 508, or state 0 when it cannot be read. Bytes 308–312, 376–448 and from 1036 to the end of the header stay zero. After the claim, Minecraft may write its camera: Unix milliseconds (u64) at 288, Unreal Pitch and Yaw (two f32 as one atomic 64-bit word) at 296 and state 1 at 304. Also only after the claim, Minecraft writes two more atomic 64-bit words: at 280 its health word, the bridged player's health share (f32 health over maximum health, in (0, 1], 0 for none: dead, link not entered or not controlled) then the heal count (u32) whose heals it has applied; at 312 its gains word, Beta then Burst base points (u32 each), its cumulative totals since its start, wrapping. The adapter reads them only with a camera it would use (state 1, time within 200 ms, finite angles in range) while forwarded input belongs to the same RUN, and writes only aligned f32 stores into the player actor's stat array (the gauges' chain and life states). Gains: each frame with those words it takes each total's u32 step since the totals it last saw; a first sighting or a step above 10000 (a restarted or foreign Minecraft) adopts the totals without granting, and the totals are adopted before the write, so a step lands once. A frame whose words are stale grants nothing and keeps the totals, so their step lands with the next fresh words; once forwarded input leaves the RUN or the stream stops, the totals are forgotten. A step of `p` points goes into Beta (stat 14) and, while `int(stat 116) > 0`, Burst (18) as Stellar Blade's `FSBActor::AddStat` adds a hit's: with the rate (stat 64 for Beta, 111 for Burst, finite within ±100000) at most 0.4 or 0.75 and `m = |trunc(rate × 1000)|`, the gain is `p` plus `ceil(trunc(m × p / 100) / 10)` with the rate's sign (never below 0), and `value = int(value + gain)`, 0 below 1, at most `int(max)`; nothing is written unless the gauges read as above. Health: Stellar Blade HP (stat 1) carries Minecraft's share of MaxHP (stat 2): MaxHP at a share of 1, else `floor(share × MaxHP)` within `ceil(MaxHP / 4)` and `MaxHP − max(1, ceil(MaxHP / 1000))` (at least the quarter), so it is never 0 and stays below full for Stellar Blade's per-mille "HP below maximum" heal condition; HP must be finite within 0–MaxHP and MaxHP within 1–100000. While mirrored, HP read more than 0.5 above the adapter's last written or seen value adds its rounded rise to the heal count, also while the share is stale; a drop below it counts one loss and is overwritten. The adapter writes only with a usable share (fresh, finite, in (0, 1]) and, after its first write, only once the acknowledged count equals its heal count, so a stale share never erases a heal Minecraft has not applied; Minecraft heals `points × maxHealth / MaxHP` and answers with its new share and the count. After 1 s without a usable share (stream stopped, Minecraft dead, link left, Stellar Blade paused or in a cutscene, Minecraft closed) the adapter writes back the HP read before its first write, at least 1, and stops; another player actor drops the record without a write. While no player actor is spawned the record waits, and her HP on her return is a new base, not a heal. While forwarded input belongs to the same RUN, the adapter turns the game's camera toward a look no older than 200 ms, with finite angles and pitch within ±90 degrees. Yaw goes through the pawn's `AddControllerYawInput` (the game's own look input path, divided by the published scale): each frame Minecraft's motion since the previous frame plus 15 % of the remaining gap to `ControlRotation`, at most 45 degrees. Pitch goes to the game's camera dolly, which carries its camera pitch (`ControlRotation`'s pitch does not track it), while the arm's next pitch follows the dolly's alpha alone: the pawn's `CameraBoom` (+0x5c0) is a live object whose virtual table is `USBSpringArmComponent`'s (RVA 0x5ce42a0) and whose owner (+0xb0) is the pawn; it uses the dolly (`bUseCameraDolly`, +0x2f4) with a `CameraDollyTrackData` (+0x2f8), is in dolly mode (`bLastUseCharacterControllerRot`, +0x370, clear), is not easing its rotation after a mode change (`RemainBlendCamera`, +0x374, at most 0), has no rotation lag (`bEnableCameraRotationLag`, bit 6 of +0x284), is on its default spline (`CurrentDollyMode`, +0x3e0, −1) and blends none (`DollyBlends` count, +0x3d8, 0); the pawn is neither aiming (`bTPSMode`, +0x1528) nor fishing (`FishingModeType`, +0x1690), and its slope camera does not set the alpha (it does while, in `MovementCheckInfo` at +0x1770, `CameraSlopeMoveType` +0x3ec and `bRunCameraSlopeMoveAlpha` +0x3ed are set and `CurrentCameraSlopeMoveRunningTime` +0x3f4 exceeds `CameraSlopeRunTimeFromStart` +0x3fc). Then the adapter adds 1/300 per degree from the arm's last pitch (`PreviousDesiredRot.Pitch`, +0x2c0, taken within ±180) to Minecraft's to `CameraDollyAlpha` (+0x2f0, kept within 0–1), ends the game's dolly blend (+0x3c0..+0x3c7 = 0, +0x3c8 = −1) and sends no pitch input; when a write moved the alpha by more than 0.0001 and the next frame finds the same alpha and the same arm pitch (the arm has not updated: the game paused or hitching), it writes nothing until the arm updates, still with no pitch input. Otherwise Minecraft's pitch motion goes through `AddControllerPitchInput` (divided by the published scale, at most 45 degrees). Minecraft writes yaw within one turn. After 60 consecutive frames with a yaw gap above 30 degrees the adapter stops adding look input until the gap closes; it still sets the dolly meanwhile. The pawn must be the live object of its published class for both; for look input its virtual table and both functions must also lie inside the game image. A slot holds counter (u64) at 0, publication Unix milliseconds (u64) at 8, generation (u64) at 16, format 5 at 24 (Minecraft refuses any other; 5 adds 256 KiB slots and the cloth below to format 4's adapter report at 488–1036 and Minecraft's words at 280 and 312, format 3's dolly refusal at 56, its header shot count at 484 and format 2's hidden bit), component count at 28, payload floats at 32, controller status at 36 (bit 0 rotation read, bit 1 camera turned toward Minecraft's this frame, bit 2 camera dolly set from Minecraft's pitch this frame, bit 3 this run owned forwarded input this frame: Stellar Blade granted it, so it was neither paused nor in a cutscene) with its Pitch, Yaw and Roll (f32 degrees, read before this frame's turn) at 40 and, with bit 2, the camera's Unreal pitch (f32 degrees, read before the dolly was set) at 52, else zero, then why the dolly was left to pitch input that frame at 56 (u32: 0 when not tried or set; 1 no camera boom, 2 dolly unused or without a track, 3 arm following the controller, 4 easing after a mode change, 5 rotation lag, 6 another spline or a spline blend, 7 TPS aim, 8 fishing, 9 slope camera, 10 unreadable alpha or arm pitch; never with bit 2), the cloth particle count n at 60 (u32, 0 for none), one status word per component at 64 (bit 0 world, 1 bones, 2 morphs, 3 hidden, 4 cloth: only on the table's `CLOTH` component, read this frame, and only with n above 0) and the payload at 128: per component its world transform, its bone transforms in component space, then its morph weights; after the last component, each parameter's floats (zeros unless the instance is live with its class and the element still carries the name; elements are 36-byte scalar or 48-byte vector parameter values, value at +16); then, with effects, 8 records of 11 floats: the index of an active effect's asset (-1 for none) and its component's world transform, for live Niagara or Cascade components of those classes attached directly to a live listed component, active, not hidden (as components are) and playing a listed asset; then, with n above 0, Stellar Blade's finished cloth of the `CLOTH` component after the payload floats counted at 32: its `ComponentRelativeTransform` (10 floats, simulation space to component space), then its n particle positions (3 floats each, simulation space, Unreal cm; particle i is render vertex i). The adapter reads them from the component's `CurrentSimulationData` (+0xe20, `TMap<int32, FClothSimulData>` written on the game thread by the cloth writeback) only when it holds exactly one element (`ArrayNum` +8 is 1, `NumFreeIndices` +0x34 is 0) with key 0, whose `Positions` (value +0x10: data, count, capacity) are non-null with a positive count within their capacity, and only when the 10 + 3n floats fit the slot. Minecraft draws vertex i at particle i (all its bones' rows the component's own transform, the positions as morph deltas, normals recomputed from the moved triangles) only while n equals the pack mesh's vertex count and the rotation is a unit quaternion, else, and while the particles stay bit for bit unchanged over 6 samples while the leader's `Bip001-Head` moves, it skins that mesh to its bones. It drops a pose whose first drawn component (EVE's body) lacks its world or bones; any other component without its data or its leader's bones, or hidden, is left out of that pose's drawing, and drawn again once two consecutive poses carry it. A transform is 10 floats: quaternion xyzw, translation xyz, scale xyz, Unreal space. Minecraft decodes a slot only with the table of the same generation.

## Combat events

On each damage to the bridged player from an attacker or projectile, Minecraft replaces [`eve-combat.txt`](fixtures/combat-event.txt): SESSION (the terrain link's), SEQ (increasing within the session, repeated by `END`), TIME in Unix milliseconds, then `EVENT kind yaw` with kind `perfect_dodge`, `perfect_parry`, `parry`, `guard`, `guard_strong` (a guarded attack of at least 8 damage), `hit` or `hit_strong` (a landed attack of at least 8 damage; both strong forms count the damage before EVE's reductions) and the Unreal world yaw in degrees (one decimal, within ±180) from EVE toward the attack's origin, or `none`. A plain dodge publishes nothing. Lua reads it each native frame and acts once per SEQ, only for the entered link's session and within 2.5 seconds of TIME: a perfect dodge plays EVE's `CH_P_EVE_01/Skill/P_Eve_Sword_Normal_JustEvade1` Show through her `SBShowActorInterface.PlaySingleShow`, toward a point 3 m along the yaw, with its full-body key's `bStopAtMove` lifted until the key has started (restored 0.2 s later, retried every frame), since the game's skill blocks movement during it and a lone Show does not; if no new evade effect is on her body mesh 0.2 s later, Lua sets Stellar Blade's global time dilation to 0.3 for half a second of real time (unless the game already runs dilated) and plays the evade Niagara systems instead; a perfect parry plays the two Shows Stellar Blade plays on EVE at a just parry, her own result `CH_P_EVE_01/Skill/P_Eve_Sword_Normal_Guard1_JustParry` and the attacker's `Result/Result_JustParry_FX` (`FX_Parry_Just`), and the bare parry Niagara system only if the latter fails; a parry plays `Result/Result_Parry_Back`; a guard plays `Result/Result_Guard_Back` (`guard_strong`: `Result/Result_Guard_Back_Strong`) with the body key `SBShowAnimKey_0`'s `bCheckHitLevel` lifted in memory for the call, which reads it while building the Show, and restored right after it (retried every frame if that fails); a hit with a yaw makes EVE react, at most every 0.6 seconds and one at a time, through the stock `Hit/Result_Hit_Stand_LightAttack` Show (`hit_strong`: `Hit/Result_Hit_Stand_StrongAttack`, or the light one if it cannot be loaded) by one of three variants (`SBBlueprintLibrary.PlaySBShowToPlayerCharacter`; `PlaySingleShow` with `bCheckHitLevel` lifted in memory on the full-body key Stellar Blade picks for the attack's angle, `SBShowAnimKey_2` within 45 degrees of EVE's facing for the light Show and 50 for the strong one, else `SBShowAnimKey_1`; `PlaySingleShow` with `AdditivePlay` counted into EVE's transient `ShowKeyTagMap`), each undone 1.1 s later and retried until it is; variants take turns, whatever the strength, until one shows a custom-animation alpha from none before, which is kept for both, and stop after 12 counted tries without one (a try while EVE already animates or moves is not counted). The perfect-dodge Show applies its Effect keys as in the game (invulnerability while it plays, Burst gauge, the just-evade counter flag) and the just-parry Show its movement block; a Show's SkillResult key has no effect, and no Show grants a parry's Beta: the adapter adds it from Minecraft's verdicts through the pose stream. The other Shows have no Effect key. Version 1 events are refused. Leaving the link restores time at once; a failed restore is retried every frame. Stopping the bridge deletes the file.

## Lock-on target

While Minecraft's lock-on holds a target, it replaces [`eve-lock.txt`](fixtures/lock.txt) every 50 ms: SESSION, SEQ (increasing, repeated by `END`), TIME in Unix milliseconds and `TARGET x y z`, the target's centre in blocks relative to the bridge origin (Minecraft axes, three decimals, within ±4096), or `TARGET none` once released. Lua takes a newer SEQ of the entered link's session (a first one only within 2.5 seconds of TIME) and keeps the lock for 0.6 seconds after the newest: it spawns a hidden, collisionless, tickless bare `SBCharacter` with an enemy tribe of EVE's (`SupplyNPC` for `PC`), keeps it at the target's Unreal position (anchor + (x, z, y) × scale), sets EVE's `LockOnCharacter` and `bLockOn` with Stellar Blade's lock-on camera off (`bLockOnCameraEnable`) and clears her off-screen timer each frame, so Stellar Blade's own lock-on faces and strafes her, and draws her sword with Stellar Blade's own draw and unfold Shows (the unfold and fold Shows of the `EquipmentTable` row her `EquipmentDataList` names at `EquipmentType_Weapon` (the list follows `ESBEquipmentType`), `LightSword1`'s `Weapon/Eve/NonPonyTail/*_NonTail` copies while her `bHidePonyTail` is set, as the game picks them, and `LightSword1`'s own for an unknown row or a Show that does not play), checked every second while the game is not in battle and does not force it folded (a draw that did not stick is retried with the draw's attach event sent at once, five tries in a row at most) and sheathed once on release if Lua drew it; a lock the game drops is engaged again at once, then at most every 0.25 s while the game refuses it; spawn, follow and engage errors together stop new locks after three. Release, staleness, link loss, F11 or an error releases through the game (target unavailable), restores the camera flag and destroys the proxy, retried every frame until done. The native adapter reads the same file: while it names a target for the session Lua's component table links, with a TIME at most 0.6 s old, and input is forwarded, EVE's lock-gated evade commands take Stellar Blade's lock-on rows (side steps) instead of the plain ones, since the game's own lock target stays empty; each changed command flag is restored on release, staleness or the end of forwarding (one out of her command tree at that moment once it is back). When that condition starts and when it ends, the adapter also walks Stellar Blade's table registry (the table manager at the global RVA 0x7032510, registry at +0x20: a `TMap<int32, TWeakObjectPtr<UDataTable>>` at +0x08 and, while byte +0x58 is 1, a second one at +0x60; key 4 is CharacterMoveTable, key 0 SkillTable; each weak pointer resolved through `GUObjectArray` with its serial number, live items only; rows from each table's `RowMap` at +0x30, by their ID at row +0x10). While the condition holds, `RotationType` (+0xBC) of CharacterMoveTable rows 1000601 and 1000701 (the lock evades' second rule move, `Target`) and `RotateInputDirection` (+0x170) of SkillTable rows 1001104, 1001105, 1001106, 1004202 and 1007102 (the sword, Tachy and Fusion lock evades) go from 1 to 0, and back from 0 to 1 once it ends; a row is written only while it still matches its shipped values (move rows `RotationEndTime` 0.3, `DistanceToIgnoreRotationLimitAngle` 280 and `RotationLeftLimitAngle` 65; skill rows `RotateInputDirectionIgnoreLockOn` 0 and `bSwitchBattleMode` 1), any other value is left alone, and a walk that faults is retried at the next frame. Stellar Blade reads these rows by name at each use, so while locked a lock evade neither turns EVE toward the stick at its start nor, with no simulation lock target, toward the nearest Stellar Blade enemy within 30 m during its second rule move. Lua, each frame while EVE is locked on the proxy, clears her `bSoftDisableLockOnCharacterRotation`: Stellar Blade sets it when a lock-rotation-disabling skill step ends while she does not face her lock target and otherwise keeps it until a move key, which would freeze her facing. Under the same condition, while EVE is in battle mode (player actor byte +0xB58 is 1, as after an attack), it writes the turn clock's time (the turn manager at the global RVA 0x7032560, checked by its virtual table RVA 0x5bf9120, f32 seconds at +0xc) to her battle-stance stamp (+0x558) when that time is finite and newer, as Stellar Blade's actor update does while its own lock target holds battle mode; it writes nothing else, and once it stops Stellar Blade ends battle mode and sheathes her `BattleStanceCancelTime` (3 s) after the last stamp. Stopping the bridge deletes the file.

## Mob walls

While EVE's position is applied, Minecraft replaces [`eve-mobs.txt`](fixtures/mobs.txt) whenever the walls change and every client tick (clients tick at the world's rate, which a perfect dodge lowers): SESSION, SEQ (increasing, repeated by `END`), TIME in Unix milliseconds, `COUNT n` (0 to 8), then n lines `MOB minX minY minZ maxX maxY maxZ`: the nearest living entities that EVE's body shoves and that intersect the terrain window, clipped to it, relative to the bridge origin in blocks (Minecraft axes, three decimals, within ±2048, every side at least 0.01). An empty list is written once, then nothing until an entity is back. Lua takes a newer SEQ of the entered link's session (a first one only within 2.5 seconds of TIME) and keeps the list for 0.6 seconds after the newest: one TriggerBox per box at its Unreal position (anchor + (x, z, y) × scale), WorldDynamic, ignoring every channel except the object type of EVE's capsule, which it blocks, query-only, without overlap events or character step-up. A box that would intersect EVE's capsule is placed without collision until she has left it, and every box is without collision while Stellar Blade lets her pass through characters (`bIgnoreCharacterCollision`, during her evades); unused boxes stay parked without collision. A box is owned before its setup, and a move or collision mode that does not take is an error. Walls are WorldDynamic objects, so a Stellar Blade query by object type (rather than by channel) may still find them. Staleness, link loss, F11 or an error destroys every box, retried every frame until done; three spawn or placement errors stop new walls. Stopping the bridge deletes the file.

## Session requests

`/stellar import`, `/stellar enter` and `/stellar return` replace [`eve-request.txt`](fixtures/request.txt): SESSION (the terrain link's), SEQ (increasing within the session, repeated by `END`), TIME in Unix milliseconds and `ACTION import`, `enter` or `return`. Minecraft sends one at a time, while a bridge session is active, from the linked player's own client. Lua checks the file on its 200 ms bridge timer and takes a request once: within 2.5 seconds of TIME, and with a newer SEQ when it comes from the session of the last request it took. `import` needs the session `terrain.txt` names, and no linked session of another; `enter` needs a current link (imported or entered) of the same session; `return` runs unless another session is linked, so a failed return can be retried like F11. A request that passes runs the same action as F5 (`sbmc mirror`), F8 (`sbmc enter`) or F11 (`sbmc restore`) on the game thread, with the same checks, log lines and cleanup; one that does not is refused without running. Lua answers every request it takes in [`eve-request-ack.txt`](fixtures/request-ack.txt) (written beside it, then renamed into place after removing the previous answer; Minecraft takes a missing answer as none yet): SESSION, SEQ and ACTION of the request, `RESULT ok`, `failed` or `refused`, `MESSAGE` and the action's message as one line of 1 to 400 printable ASCII characters (others become `?`, an empty one `-`), then `END` with the SEQ. Minecraft shows the answer whose SESSION, SEQ and ACTION match its pending request in chat; after 5 seconds without one it reports no answer and accepts the next request, since Lua's whole-second wall clock cannot take a request more than 3.5 seconds after its TIME. Stopping the bridge deletes both files.

## HUD and items

While a link is entered, Lua publishes [`eve-hud.0` and `eve-hud.1`](fixtures/hud.txt) on its 200 ms bridge timer when the content changes and at least every wall second, written as `eve-hud.tmp` and renamed into slot SEQ % 2 after removing it: SESSION (the entered link's), SEQ (increasing within the Lua lifetime, repeated by `END`), TIME in Unix milliseconds of Lua's whole-second clock, then `HEAL kind count max usable`, `UTIL kind count cooldown usable`, `AMMO alias count ready` and `DASH ready`, each `none` when absent, and `USES shock pulse mine sonic`. A kind is `tumbler`, `potion`, `lingering`, `field`, `shock`, `pulse`, `mine`, `sonic`, `pump` or `other`; counts are integers 0–9999 (max is the Tumbler's capacity, the heal slot's `RecoveryPotionMaxCount`, else 0), cooldowns and ready shares 0–1 with two decimals (UTIL's cooldown is the share left, 0 when ready; AMMO's and DASH's values read 1 at rest, so Minecraft takes them as ready shares, 1 when ready), usable 0 or 1, an alias 1 to 64 of `[A-Za-z0-9_]`, uses 0–2147483647. The values are the reflected Blueprint variables Stellar Blade's HUD logic writes into its own widgets: the `WB_MainHUD_ItemSlot_C` instances `WB_MainHUD_HealItem` and `WB_MainHUD_UtilItem` (`ItemCount`, `RecoveryPotionMaxCount`, `CoolTimePercent`, `UseActive`, which the HUD logic clears while EVE's `ActorState_BlockItemUseHeal` or `ActorState_BlockItemUseUtil` blocks the slot, and the kind from the texture the slot draws, `ItemTable.Asset2D`: `Image_Item_Thumb`'s brush texture, else the `Icon_Texture` parameter of the dynamic material instance its `WB_MainHUD_ItemSlotGeneral` draws (`UI_IconProgress_Inst`); `Icon_PotionR` tumbler, `Icon_Potion` potion, `Icon_PotionSmall` lingering, `HealGrenade` field, `Grenade` shock, `PluseGrenade` pulse, `TrapGrenade` mine, `FlashGrenade` sonic, `WbPump` pump, any other texture (such as the Camera's `Icon_Camera`) other; the heal slot, which also holds potions and the Biotic Field, shows the Tumbler as a cup that may draw no texture, so a heal slot without one is tumbler while its `ChangeItemCategory` (the item's `ESBItemCategory`, which the HUD logic writes on each slot update) is 12, RecoveryPotion; any other slot without a texture or a readable count is none), EVE's `SBCharacter.CurrentBulletItemAlias` with the `WB_Tps_Bullet2_Slot_C` of that `ItemAlias` (`ItemCount`, `CooltimePercent`), and `WB_MainHUD_Dash_Slot_C.CoolTimeProgress`. Lua keeps the live widgets while they are valid, never the designer templates `FindAllOf` also lists (in their widget class's own `WidgetTree`, with the Blueprint defaults); since `FindAllOf` walks every object on the game thread, a missing one is looked for again 2 seconds later, then after twice as long up to 30 seconds (2 seconds again once a search finds one), and at once when a found one goes. A util count that drops while the kind stays the same adds the drop to that kind's use counter (shock, pulse, mine and sonic); a rise (a refill) or another kind (a selection) adds nothing, so a last unit whose slot at once shows another item is not counted. A read counts only once the next read agrees with it, since Stellar Blade writes the count and the thumbnail apart, and a newly found util widget starts again from its own values.

Minecraft reads both slots each client tick while EVE replaces the player, takes the newer SEQ of the applied link's session and uses it within 2.5 seconds of TIME; a missing or stale file only hides the slots. A use counter step of 1 to 3 is that many new uses (a first sighting, a decrease after a Lua reload or a larger step converts nothing), each applied on the server thread while the bridge overrides the player, to every entity EVE may strike within 3.25 blocks of the player (Stellar Blade's 325 cm): Shock knocks it back and adds Slowness VII and Weakness X for 1.5 seconds; Sonic knocks it back and adds Slowness II and Weakness II for 5 seconds; Pulse knocks it back, removes Absorption and Resistance and deals 12 % of its maximum health as the player's indirect magic; a Smart Mine is placed half a block ahead of the player (three at most, the oldest dropped, gone after a minute or with the override), arms when a monster comes within 2 blocks and 10 ticks later strikes as a strong blade strike, with knockback. Nothing damages blocks or the player. Heal-slot items and the Biotic Field need no conversion: Stellar Blade heals EVE's mirrored HP and Minecraft takes the heal from the pose stream.

## Wardrobe

Minecraft replaces [`eve-wardrobe-request.txt`](fixtures/wardrobe-request.txt) (at most 512 bytes) to list what EVE owns or to change what she wears: SESSION (the entered link's), SEQ (1 to 15 digits, increasing within the session, repeated by `END`), TIME in Unix milliseconds, `OP list`, `equip` or `unequip`, `SLOT` (the `ESBEquipType`: 0 for `list`, else 1 to 17) and `ITEM` (the item's `SavedGuid` as 32 lowercase hex digits, its four dwords in memory order, not all zero, for `equip`; `-` otherwise). A request names a target state, so a replay is harmless. The native adapter reads the file every 20 ms and takes a request once: while the pose stream is active, of the session Lua's component table links, within 2.5 seconds of TIME and with a SEQ above the last one taken of that session; any other request gets no answer. A newer request replaces one not started yet. At its gameplay poll, after the gauge grants and the HP mirror, the adapter runs the gates in order, each refusal answered as `refused <reason>`:

1. Lua's control permit is active for the stream's run (not merely forwarded input: an open Minecraft screen suspends that): `not-playing`.
2. The game world and the table manager (`TableManagerRva`) are set, the player actor is spawned, the item manager (world +0xE8) is set, and Stellar Blade's player GUID (RVA 0x1cc2590) has an Inventory bucket (RVA 0x1cc1110, type 1): `not-ready`. `list` stops here, answered `listed`.
3. Stellar Blade's equipment menu's own slot-entry checks, in its order (0x1dbd7e0): `HasActorState` (RVA 0x1a64b40) TachyMode (0x48) gives `tachy`, Fusion2Mode (0x5d) or Fusion1Mode (0x5c) `fusion`, and the menu's combat test (RVA 0x1a90c30) `combat`.
4. The slot rule: `equip` only into a wardrobe slot (1 to 8, 10, 11, 17) that holds an item now, or into the earring (10) or face accessory (11) slot; `unequip` only 10 or 11, so the nano suit and hair are never emptied and empty gear or exospine slots, which may be locked, stay out of reach: `slot`.
5. For `equip`: the item is in the bucket and its `ItemTable` row (RVA 0x1a9a960, `Category` at +0x70) fits the slot (Gear 2 into 1-4, ExoSpine 3 into 6 or 7, NanoSuit 4 into 5, Hair 21 into 8, FaceAccessory 22 into 11, EarRing 23 into 10, Drone 28 into 17): `not-owned`.

A slot that already holds the item (`equip`) or nothing (`unequip`) is answered `unchanged` without a call. Otherwise the adapter calls Stellar Blade's menu equip, `EquipOwnedItem` (RVA 0x1cc1490, with the worn hair's `MatVarIndex` for slot 8 and 0 otherwise, as the menu and the hair salon do) or the menu's unequip (RVA 0x1cc18f0): one call per poll, on the game thread, contained like the adapter's reads. Stellar Blade queues the change and applies its own checks (allowed slot, DLC condition, exospine family, suit-change block) at its next logic step; a check that fails changes nothing. The adapter then reads the player actor's worn map (`TMap<int32, FSBItemInstance>` at +0x3E8) at each poll until the slot holds the item (`equipped`) or nothing (`unequipped`), or for one second (`unchanged`).

A structured exception in any of this (a read of Stellar Blade's memory, or one of its own calls, that faults) is contained and answered `refused fault-<stage>-<code>`: the step that raised it, `owner` (step 2), `tachy`, `fusion` or `combat` (step 3), `slot` (step 4), `item` (step 5), `equip` or `unequip` (the call), `done` (the worn map read during the wait, answered instead of `unchanged` when the wait ends without the change) or `list` (the owned list, answered instead of any result that names no fault), then the exception code as 8 lowercase hex digits (`c0000005` for an access violation); a fault before the wait adds `-<rva>-<data>`, the faulting instruction's address relative to Stellar Blade's image and the access violation's data address (`ffffffff` for a misaligned SSE load under Wine), each the low 32 bits as 8 lowercase hex digits. A fault before the wait, or in the owned list itself, answers with no items. A genuine step 2 failure stays `refused not-ready`.

The adapter answers each request it took by replacing [`eve-wardrobe.txt`](fixtures/wardrobe.txt) (at most 64 KiB): SESSION and SEQ of the request, TIME in Unix milliseconds, `RESULT listed`, `equipped`, `unequipped`, `unchanged` or `refused <reason>`, `COUNT n` (0 to 1024) and n lines `ITEM id category guid level variant slot`: the `ItemTable` row ID and `ESBItemCategory`, the `SavedGuid` (as in the request), `StatLevel` (0 to 9999), `MatVarIndex` (0 to 99) and the slot the item is worn in, or 0. The lines list every Inventory bucket item of the seven wardrobe categories, then each worn one the bucket lacks, read when the answer is made; a refusal before the bucket was found lists nothing. The adapter keeps the file after a session ends: it is the last owned list. Another version, a bad footer or a COUNT that does not match makes the answer unreadable.

Minecraft writes the request from its wardrobe screen, which opens only while EVE replaces the player, with the session of its entered link and one SEQ counter for the whole Minecraft run, and waits for the answer of that SESSION and SEQ for 5 seconds; it also refuses an `ITEM` line outside the seven wardrobe categories, and a `refused` reason other than those above (a fault's stage among the ten named, its code exactly 8 lowercase hex digits). `/stellar stop` deletes the request and keeps the answer.

## Minecraft network protocol

The bridge's server and client halves talk through Fabric payloads on `stellar_bridge:` channels, versioned by one integer, `BridgeNet.PROTOCOL` (2: remote EVE poses; 1 had none), raised on any payload change. Nothing from Stellar Blade crosses the network: no file above travels as is, and each client writes its own bridge directory with its own clock.

Handshake, in the configuration phase: when the client can receive `hello`, the server sends `hello` (varint protocol, mod version of at most 256 characters) as a configuration task and waits for the client's `hello` back with its own; another protocol disconnects the client with both protocols and versions named. `hello` keeps this layout in every protocol. A client without the mod, or with it but facing a server without it, joins as usual: no `hello` is sent, and EVE players look like vanilla players to it.

Play payloads, registered on both sides (doubles and floats as IEEE, integers big-endian, varints as Minecraft's; a decoder refuses any count, length, enum or flag beyond its bound, and non-finite stats):

| Payload | Direction | Content |
|---|---|---|
| `link_request` | C2S | action byte: `/stellar start` 0, `stop` 1, `status` 2, the pose relay's counts for `/stellaravatar status` 3 |
| `link` | S2C | session (32 hex, empty for none), origin (3 doubles), dimension, message (the reason when ended) |
| `eve` | C2S | an `eve.N` packet as Lua wrote it (at most 65536 characters), the client's wall clock at sending (Unix milliseconds) |
| `terrain` | S2C | a terrain snapshot without TIME: session, revision, dimension, origin, bounds and at most 1024 boxes (6 doubles each); the client stamps TIME |
| `mobs` | S2C | at most 8 mob wall boxes relative to the origin, sent when they change |
| `strike` | C2S | varint entity id, style byte (swing 0, light 1, strong 2, thrust 3, shot 4), flags (charged 1, first 2, quiet 4), and for a shot the hit point (3 doubles); the server computes the damage |
| `defense` | C2S | edge byte (dodge 0, guard down 1, guard up 2), when it happened and when it was sent, both on the client's monotonic nanosecond clock; sent at each new press and at the guard's release |
| `item` | C2S | kind byte (shock 0, pulse 1, mine 2, sonic 3) |
| `status` | C2S | EVE's 8 stats as floats (or none), the adapter's heal count (-1 for none, else a u32), and whether Stellar Blade withholds her input (paused, a cutscene); sent when it changes |
| `verdict` | S2C | combat event byte (the index in `perfect_dodge`, `perfect_parry`, `parry`, `guard`, `guard_strong`, `hit`, `hit_strong`) and the attacker's yaw (NaN for none) |
| `feedback` | S2C | health share and heal count applied, Beta and Burst earned on this connection (cumulative from 0, wrapping); sent when it changes |
| `table` | C2S | the sender's EVE as a names-only component table (below), at most 65536 bytes; sent for each new generation while she is anchored to the link |
| `pose` | C2S | one network pose (below), at most 16384 bytes; 20 a second by default |
| `remote_table` | S2C | owner UUID, then another player's `table` as it came; also when the viewer starts tracking that player |
| `remote_pose` | S2C | owner UUID, then another player's `pose` as it came |

The server keeps one link session per player and checks `link_request` for that player: alive, not a spectator, not riding, with the handshake done; beyond 2 requests a second they are refused and counted, since a payload skips vanilla's command spam limit. Its answers come as chat lines; a session that starts or ends sends `link`. The player's client then owns the files above in its own bridge directory: it relays each new `eve.N` packet once (`eve`), and writes `terrain.txt`, `eve-mobs.txt` and `eve-combat.txt` from `terrain`, `mobs` and `verdict`, and `eve-lock.txt` and the session requests itself, every TIME stamped with its own clock; it applies EVE's position from the same packet with the server's gate rules, so the player never waits for the server. Singleplayer goes through the same payloads over the integrated connection. A server never takes a client timestamp for its own: it compares a client's timestamps with that client's other ones, and reads an `eve` packet's TIME by the sender's clock, offset by the payload's sending time against its arrival (transit only makes a packet look older).

Combat is judged on the server, per player. A `strike` names the entity and the style; the server computes the damage and refuses (and counts) a strike unless EVE drives the player, the target is strikable in that world, within 6 blocks of the player's feet (35 for a shot, whose hit point must lie within a block of the target's box with no block before it from the eyes), within 40 strikes or 10 shots a second, and at least 0.2 s after the player's last strike on that target. Item uses are capped at 3 a second per kind and act at the server's position of the player. A `defense` edge is placed on the server's clock at its arrival less its wait on the client (`sent` minus `at`, refused outside 0 to 250 ms) and the player's allowance: their latency as the server measures it (its smoothed keep-alive round trip), at most 150 ms. A press made before an impact as the player saw it therefore counts though it arrives after the impact. When the allowance is 20 ms or more, a hit no press answers yet is held until the allowance has passed, then judged at the start of the next server tick against the presses placed before its impact. The singleplayer host's client shares the server's clock: its stamps count as they are, with no allowance and no hold, and only a future one or one older than 2 seconds is refused, since its wait includes the server's own stalls. Every verdict except a plain dodge goes to the defender's client as `verdict`; a perfect dodge's starts the client's 1.5 s tint. See [BridgeNet.java](../minecraft/src/main/java/org/stellarbridge/BridgeNet.java) and [BridgeLink.java](../minecraft/src/main/java/org/stellarbridge/BridgeLink.java).

### Network pose

Each EVE player's client streams her pose to the server, which relays it to the other modded players with an avatar pack. Only names and quantized numbers travel: no mesh, texture or other game asset, and no Stellar Blade process address (the component table is re-encoded from the parsed stream table, never forwarded as text). Integers are big-endian, varints are unsigned LEB128, names are ASCII. A decoder refuses any count, name, bit, index, length or trailing byte beyond the bounds below; the server checks a whole `table` and a `pose`'s header, and never decodes a pose body.

`table` (one per generation): i64 generation, the sender's Minecraft origin (3 f64), Unreal units per block (f64), dimension (u8 length, an identifier), flags (u8: 1 when poses carry effects), component count (u8, 1 to 16), and per component: name, mesh, leader (empty when it carries its own bones), u16 bone count and bone names (at most 512, none for a follower), u16 morph count and morph names (at most 1024), and an i64 fingerprint, the first 8 bytes of the SHA-256 of the sender's `<mesh>.sbav` (0 when unknown), so a viewer can tell whether its own copy of that mesh is the same; then u8 effect asset count (at most 32) and their names. Names use Lua's token set (printable ASCII without spaces, at most 128 characters); mesh names are `[A-Za-z0-9_.-]{1,96}`. A table's decoded pose layout is at most 65504 floats, the stream's slot capacity.

`pose`: kind byte (keyframe 0, delta 1), varint table generation, varint sequence (counting up from 1; a viewer starts counting again with each `table`, which always comes before its poses), for a delta the varint sequence of its base, i64 Stellar Blade publication time (Unix milliseconds, the sender's clock), then the body, deflated. The body is: u8 component count, one status byte per component (world 1, bones 2, morphs 4, hidden 8; cloth never travels, so remote ponytails follow their bones), then per component its world transform when world is set (translation relative to the link anchor in Unreal centimeters as 3 f32, rotation, scale as 3 i16 in 1/4096), its bones in component space when bones is set (each a rotation, translation as 3 i16 in 1/32 cm, scale as 3 i16 in 1/4096), its morph weights when morphs is set (i16 in 1/16384), then u8 effect slot count, 8 when poses carry effects and the first component's world transform is set, else 0, and per slot an asset index (u8, 255 for an empty slot) and the effect's position relative to the first component's translation (3 i16 in 1/8 cm, zeros in an empty slot; an effect beyond about 40 m is left out, its slot empty). The slots are fixed so that an effect starting or ending keeps the body's length. A rotation is the smallest three components of the unit quaternion with the largest made positive: its index in 2 bits, then the others in 15 bits each over ±1/√2 (6 bytes). The worst errors are 0.0066° of rotation, 1/64 cm of translation, 1/8192 of scale and 1/32768 of a morph weight. A viewer dequantizes a pose into the stream's own float layout (absent transforms are the identity, absent effect records have index -1) with the table at anchor 0, so the stream's decoder, interpolation and effects take it unchanged; material parameters do not travel. It draws each mesh its own pack holds with the sender's fingerprint (or an unknown one); for a mesh it lacks or holds in another version it draws its role's core mesh, driven by bone name, or nothing. It hides that player's vanilla body, not their name tag, only while their EVE shows her body within 8 blocks of the player, and draws no EVE for a player invisible to it. It draws each pose at its arrival clock less the remote's clock floor (the least arrival minus publication seen, rising 1 ms a second, or at once to the least of a 5 s window that stays 250 ms above it: a clock step) and 1.5 intervals, so transit, jitter and the sender's clock offset cancel.

Delta coding: the sender sends a keyframe every 10 poses (`-Dstellarbridge.poseKeyframes`), at a new generation or a new link, and whenever the body's length changes (a status change; effects fill fixed slots and never change it); in between, a delta is the body minus the previous pose's body, byte by byte (mod 256), deflated. A viewer decodes a delta only on the pose it was made from, the last one it decoded; any other delta, and any pose older than that, is dropped, so a lost or reordered delta costs at most the poses until the next keyframe. The sender sends the newest sample of its stream at most 20 times a second (`-Dstellarbridge.poseRate`, 1 to 30), and only while EVE is anchored to its link, not in a singleplayer world closed to LAN (where only the development echo and recording get them).

Relay: the server caches each player's latest `table` and sends it to every player tracking that player, at once and whenever one starts tracking them; a pose of another generation than the cached table, or beyond 35 poses or 128 KiB a second from one sender (a quarter of a viewer's budget), is not relayed, and a sender's tables go out at most 2 a second, one over that waiting for the sender's next pose (only the latest goes), so one client cannot use up its viewers' budgets or keep their outfits rebuilding. A pose goes, as the bytes it came in, to each player tracking its sender whose client listens (a client without the mod or without an avatar pack does not), within 64 blocks every pose, beyond keyframes only (2 a second). A delta goes to a viewer only when that viewer got its base; after a pose withheld (far, or a viewer that just started tracking) or dropped over the viewer's budget (512 KiB a second by default, `-Dstellarbridge.relayBudget` in KiB on the server), the viewer gets that sender's next keyframe first.

Bandwidth: a 466-bone outfit's keyframe measured 4,867 bytes deflated and byte deltas 1,966 to 2,851 bytes (29 to 163 ms apart), so a stream at 20 Hz takes about 50 KB/s (0.4 Mbit/s; keyframes only would take 97 KB/s) and 10 KB/s beyond 64 blocks. With 8 players all in view each uploads 0.4 Mbit/s, each viewer receives about 2.8 Mbit/s and the server sends about 22 Mbit/s. Combat traffic stays under 1 KB/s per player. See [NetPose.java](../minecraft/src/main/java/org/stellarbridge/NetPose.java), [PoseRelay.java](../minecraft/src/main/java/org/stellarbridge/PoseRelay.java) and [RemoteEves.java](../minecraft/src/main/java/org/stellarbridge/RemoteEves.java).

## XInput callers

While its input worker runs (the pinned executable verified), the adapter rewrites [`eve-input-calls.txt`](fixtures/input-calls.txt) at most once a second: `SBMC_XINPUT_CALLS 1`, `TIME` (Unix milliseconds), `GAMEPLAY count rate`, `OTHER count rate`, `END`. The counts are its slot-0 `XInputGetState` calls since it loaded (u32, wrapping): those returning to the verified gameplay poll's call site, and those returning anywhere else (the game's device discovery, or an overlay hook calling on the game's behalf). Each rate is the count's calls per second over the interval since the previous report (monotonic clock). It is apart from the input acknowledgement, which exists only after a recognized gameplay poll, the case it diagnoses, and leaves that acknowledgement's grammar unchanged. Readers take it as fresh within 3 seconds of their clock; Minecraft only reports it.

## Text publication and legacy captures

Java publishes text with atomic replacement. On Windows a replacement is refused while a reader holds the file open (`MoveFileEx` has no POSIX rename semantics), as Lua's `io.open` (MSVC `fopen`) and the adapter do for an instant: Java retries it 5 times, 1 ms apart, then reports the failure as before; and a file just removed but still held open reads as absent, as a missing one does. Lua uses alternating slots where Windows cannot rename over an existing destination. Control permits retire the old slot under a unique owned name before publishing; cleanup failure retains ownership for retry. A missing/stale permit neutralizes input.

Frame-v1 uses PNG color; v2 uses BMP color with PNG mask and HDR depth. Frame-v3 describes a pending asynchronous still and v4 the encoded continuous compatibility path. Frame-v5 described three-job raw payloads and is no longer accepted; v6 replaces it. Pending encoded output requires observed file closure and content validation; metadata alone is insufficient. The active `/stellarview play` and `/stellarview livehd` path uses v6.

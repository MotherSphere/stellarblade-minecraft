# Architecture

## Responsibilities

Minecraft owns the world, block changes, inventory, menus and interaction handlers. It exports nearby collision shapes, receives EVE's feet position, and composites EVE's rendered image with Minecraft depth. Its targeting uses the displayed camera while reach remains measured from the player.

The UE4SS Lua mod imports a fixed terrain patch into an elevated lab, tracks the original return position, reads the native pawn/camera and manages bridge-owned capture components. Replacement collision is prepared before old collision is retired. Blocks intersecting EVE are deferred. Failed return keeps the supporting floor available.

The Windows `xinput1_3.dll` adapter verifies the complete executable identity and native callsites. It forwards physical controllers through the system XInput implementation and delivers bridge input only at the verified gameplay poll. It intercepts only registered bridge image jobs before encoding and publishes complete raw images.

## Rendering and ownership

Continuous capture uses two persistent Unreal capture components: final display color and scene depth. Captures clear unrendered pixels to the largest finite binary16 depth, so the native adapter derives coverage from depth: nearer depths are EVE, the clear value is not. A separate scene-color alpha pass matched this coverage exactly on EVE and added only background fog haze, so it is no longer rendered or read back. Capture dimensions follow the Minecraft framebuffer at run start, preserving aspect within 3840 × 2160. Restart the view to change resolution after a resize. One initial synchronous depth export establishes readiness. Subsequent jobs use the engine image queue with at most one pending capture generation; depth is submitted before color so its conversion overlaps the color readback.

Game-thread capture scheduling is checked once per native frame; terrain work retains its separate 200 ms interval. Persistent display-color captures enable the pinned TemporalAA flag locally. Fog is restricted to rendered opaque pixels. These settings do not change normal game graphics. Coverage is binary per pixel: dithered hair stays stippled, and translucent effects that write no depth are not composited.

The producer owns a back slot, the consumer owns a front slot, and an atomic exchange transfers the middle slot. Each run has a new private mapping. A slow reader obtains the latest complete image without building a frame backlog. Java copies the acquired planes into detached CPU storage before releasing the mapped slot. At most three unused color/depth pairs are retained per bus; outstanding frames keep ownership until release, even after the mapping closes.

A single Java worker checks raw availability after a 1 ms delay; encoded and inactive paths use 20 ms. The render thread consumes one latest prepared frame, reuses its GL textures and swaps camera/color/depth coherently. Stopping prevents further scheduling and releases owned resources. Metadata, dimensions, identity, reserved bytes, depth and leases remain validated.

This removes repeated image encoding/decoding and avoids per-frame buffer allocation once reusable storage is available. It does **not** remove Unreal's GPU surface readback: the hook runs after that readback, which blocks Unreal's render thread for each plane. Its cost grows with captured pixels and is the dominant cost per generation. GPU staging needs separate resource ownership and fence integration; lowering delays alone cannot provide it. Capture timing, accepted image cadence and Minecraft rendering FPS measure different things; see [diagnostics](diagnostics.md#performance-measurements).

## Avatar rendering (experimental)

The avatar path inverts the capture: Minecraft draws EVE's meshes itself from her bone poses, so her image follows Minecraft's camera and frame rate instead of Stellar Blade's capture cadence. Poses are local bone transforms per skeletal mesh component plus component world transforms; followers that use a leader pose (face, ponytail) map bones to the leader by name. Java composes component-space transforms, multiplies by inverse reference poses and the Unreal-to-Minecraft axis mapping (X, Z, Y at 100 units per block, as the terrain link uses), and uploads one affine matrix per bone. A GLSL 1.50 vertex shader blends four influences and summed morph deltas. The fragment shader keeps Minecraft's entity lighting and lightmap and adds per-material normal, surface (occlusion, roughness, metallic, specular), emissive, subsurface and hair maps from the pack, Minecraft's sky color as a reflected environment, a premultiplied translucent pass for overlays, and an additive trail between the weapon's trail sockets; the game's pooled Niagara and Cascade effects attached to EVE are read each frame (reflected offsets, live-object and class checks, `bIsActive`): the Cascade blade trails start and color the weapon trail, and the others become CPU-simulated additive sprites with the game's own effect textures, from one emitter recipe per asset (Minecraft particles when the pack has no effect textures); the tangent frame comes from screen-space derivatives, so the mesh format carries no tangents, and cut-out textures get coverage-preserving mipmaps. Textures, buffers and the shader program belong to the renderer and every GL state change is restored after drawing. Poses come from a recorded probe or from the native pose stream. For the stream, Lua names EVE's skeletal mesh components with their object, class and mesh addresses; the adapter copies their component-space bone arrays (the engine's read buffer of its double-buffered transforms), world transforms and morph weights at the verified gameplay XInput poll on the game thread, where garbage collection cannot run concurrently and the previous frame's animation and physics are final. Each read first checks `GUObjectArray` for the live, non-pending-kill object and compares class and mesh; structured exception handling contains a fault. Glow parameters that Stellar Blade's material-parameter notifies animate on dynamic material instances (the sword edge's `Opacity` and emissive color) are read the same way: Lua publishes each instance, the offset of its parameter array (by reflection), the element and the FName comparison index of its name; the adapter copies the value only while that element still carries the name. Offsets come from the pinned executable's `execSnapshotPose`, `USkeletalMeshComponent::SnapshotPose`, `execK2_GetComponentToWorld` and inlined `FUObjectArray::IndexToObject`. A frame copies about 13 KB instead of the Lua probe's 4.9 ms of reflected calls; `/stellaravatar status` reports the measured read time. Once per Minecraft frame, before the camera update, Minecraft takes the newest pose and interpolates the displayed pose one measured sample interval in the past on the adapter's publication timestamps (at most half an interval of extrapolation), so neither Minecraft's frame timing nor its polling adds jitter. The camera and the drawing share that one displayed pose. The adapter reads forwarded input every 5 ms; Minecraft publishes avatar input edges immediately.

In `/stellaravatar play` the pose stream replaces captured images as the input gate: Minecraft forwards controls only while this run's anchored pose is fresh, and Lua grants the native permit for the stream's run and the entered link. Minecraft owns the camera and writes its yaw and pitch into the pose mapping each frame. Stellar Blade's camera keeps its own state and does not follow writes to `ControlRotation`, so at the gameplay poll, before the frame's input processing, the adapter turns it the way a mouse does: it calls the pawn's virtual `AddControllerYawInput` and `AddControllerPitchInput` with Minecraft's motion since the previous frame, plus for yaw a share of the gap to `ControlRotation` (offset found by UE4SS reflection), divided by the controller's input scales. Pitch gets the motion alone: the controller's pitch does not track the game's camera pitch, so closing a pitch gap would push the camera away. The pawn passes the same `GUObjectArray` and class checks, its virtual table must lie in the game image, and this happens only while forwarded input belongs to the stream's run, which the Lua permit limits to the entered link. The game's own look handling, view limits and lock-on rules then apply. Minecraft rotates the left stick by any remaining difference and falls back to right-stick steering when the camera is not being turned.

## Input and lifetimes

EVE mode forwards Minecraft's actual configured controls. Build mode retains native look but returns click/sneak interactions to Minecraft. Input has its own heartbeat and bounded ordered press/release queue, independent of image-write completion. It requires a fresh displayed frame, matching terrain session, native permit and neutral handshake. Acknowledgement means a native gameplay poll consumed the input, not that a skill dealt damage.

Stale data, lost focus, menus and unsupported native contexts neutralize controls. Expired epochs cannot be revived by newer heartbeat traffic. Windows permit publication renames the old slot to a uniquely owned retired path before publishing its replacement; cleanup can be retried without deleting a live reader's file.

## Scope and references

Combat with the avatar works through Minecraft's damage pipeline only, so it applies to any living entity a mod adds. On the render thread, the displayed blade (the weapon trail's newest sockets) is swept each frame against the client world's living entities while the game's trail plays; each hit entity id goes to the integrated server thread, which validates the session, the entity and its reach, and damages it as the bridged player's attack (style-based amount, immunity frames cleared per strike, extra knockback). A server-player `damage` hook judges every damage with an attacker or projectile at its impact against the latest dodge and guard presses that ControlBridge publishes; a perfect dodge lowers the server tick rate for a fixed real time and restores it, also when the bridge stops. Minecraft's own collisions with EVE's forced position (suffocation, fall, cramming) are ignored. Each verdict except a plain dodge is published to Lua as a session-bound combat event, which answers in Stellar Blade with its global time dilation, its own Niagara systems spawned on EVE's mesh and EVE's own hit Show or hit animation through her `SBShowActorInterface` (only after checking she is an `SBCharacter`, since the interface call is unchecked), so the pose stream and effect probe carry them back to Minecraft. Lock-on is Minecraft's: it picks a living entity near the crosshair, outlines it through `MinecraftClient.hasOutline` and turns the player's look toward it each frame before the camera update, which the look stream then forwards to Stellar Blade.

The implementation currently limits terrain to one 9 × 6 × 9 patch and 256 merged collision boxes. Terrain is not streamed around a moving player. Stellar Blade's own defensive state and damage-driven hit reactions (the bridge plays a stock light hit, experimentally), multiplayer, Iris and arbitrary mod compatibility require additional integration. Native outfit/accessory/effect capture is not universally supported.

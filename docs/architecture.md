# Architecture

## Responsibilities

Minecraft owns the world, block changes, inventory, menus and interaction handlers. It exports nearby collision shapes, receives EVE's feet position, and composites EVE's rendered image with Minecraft depth. Its targeting uses the displayed camera while reach remains measured from the player.

The UE4SS Lua mod imports a terrain window that follows EVE into an elevated lab, tracks the original return position, reads the native pawn/camera and manages bridge-owned capture components. The anchor and the Minecraft origin stay fixed for the session; only the window moves, by whole world-aligned 8-block cells with hysteresis, and a window that cannot move (unloaded chunks, the box cap, the reach) is held with an action-bar warning while the wanted window's chunks hold a ticket too. Minecraft keeps each window from the first revision that published it until EVE acknowledges a newer one, so edits never evict the window she still acknowledges. Once the newest EVE packet is idle, ready or 30 seconds old, the window follows the anchor again, where Stellar Blade imports it. Minecraft merges collision per cell, so a block edit changes only its cell's boxes, and reuses each cell's merge while its block shapes are unchanged, so a moved window merges only its new cells; Lua rebuilds only boxes that changed, keeping actors whose exact box remains, spawns a moved window's guards first, imports boxes within a per-frame budget, and retires old collision and the old guards only once the new revision is complete. EVE's position counts only inside the window of the revision she acknowledges. Blocks intersecting EVE are deferred. Failed return keeps the supporting floor available. Minecraft's `/stellar import`, `/stellar enter` and `/stellar return` run the very actions of F5, F8 and F11 through a session-bound request file that Lua checks on its 200 ms bridge timer and answers in a status file, so a session can be driven without Stellar Blade's window and without simulated keystrokes.

The Windows `xinput1_3.dll` adapter verifies the complete executable identity and native callsites. It forwards physical controllers through the system XInput implementation and delivers bridge input only at the verified gameplay poll. It intercepts only registered bridge image jobs before encoding and publishes complete raw images.

## Rendering and ownership

Continuous capture uses two persistent Unreal capture components: final display color and scene depth. Captures clear unrendered pixels to the largest finite binary16 depth, so the native adapter derives coverage from depth: nearer depths are EVE, the clear value is not. A separate scene-color alpha pass matched this coverage exactly on EVE and added only background fog haze, so it is no longer rendered or read back. Capture dimensions follow the Minecraft framebuffer at run start, preserving aspect within 3840 × 2160. Restart the view to change resolution after a resize. One initial synchronous depth export establishes readiness. Subsequent jobs use the engine image queue with at most one pending capture generation; depth is submitted before color so its conversion overlaps the color readback.

Game-thread capture scheduling is checked once per native frame; terrain work retains its separate 200 ms interval. Persistent display-color captures enable the pinned TemporalAA flag locally. Fog is restricted to rendered opaque pixels. These settings do not change normal game graphics. Coverage is binary per pixel: dithered hair stays stippled, and translucent effects that write no depth are not composited.

The producer owns a back slot, the consumer owns a front slot, and an atomic exchange transfers the middle slot. Each run has a new private mapping. A slow reader obtains the latest complete image without building a frame backlog. Java copies the acquired planes into detached CPU storage before releasing the mapped slot. At most three unused color/depth pairs are retained per bus; outstanding frames keep ownership until release, even after the mapping closes.

A single Java worker checks raw availability after a 1 ms delay; encoded and inactive paths use 20 ms. The render thread consumes one latest prepared frame, reuses its GL textures and swaps camera/color/depth coherently. Stopping prevents further scheduling and releases owned resources. Metadata, dimensions, identity, reserved bytes, depth and leases remain validated.

This removes repeated image encoding/decoding and avoids per-frame buffer allocation once reusable storage is available. It does **not** remove Unreal's GPU surface readback: the hook runs after that readback, which blocks Unreal's render thread for each plane. Its cost grows with captured pixels and is the dominant cost per generation. GPU staging needs separate resource ownership and fence integration; lowering delays alone cannot provide it. Capture timing, accepted image cadence and Minecraft rendering FPS measure different things; see [diagnostics](diagnostics.md#performance-measurements).

## Avatar rendering (experimental)

The avatar path inverts the capture: Minecraft draws EVE's meshes itself from her bone poses, so her image follows Minecraft's camera and frame rate instead of Stellar Blade's capture cadence. Poses are local bone transforms per skeletal mesh component plus component world transforms; followers that use a leader pose (face, ponytail) map bones to the leader by name. Java composes component-space transforms, multiplies by inverse reference poses and the Unreal-to-Minecraft axis mapping (X, Z, Y at 100 units per block, as the terrain link uses), and uploads one affine matrix per bone. A GLSL 1.50 vertex shader blends four influences and summed morph deltas. The fragment shader keeps Minecraft's entity lighting and lightmap and adds per-material normal, surface (occlusion, roughness, metallic, specular), emissive, subsurface and hair maps from the pack, Minecraft's sky color as a reflected environment, a premultiplied translucent pass for overlays, and an additive trail between the weapon's trail sockets; the game's pooled Niagara and Cascade effects attached to EVE are read each frame (reflected offsets, live-object and class checks, `bIsActive`): the Cascade blade trails start and color the weapon trail, and the others become CPU-simulated additive sprites with the game's own effect textures, from one emitter recipe per asset (Minecraft particles when the pack has no effect textures); the tangent frame comes from screen-space derivatives, so the mesh format carries no tangents, and cut-out textures get coverage-preserving mipmaps; hair blends its strands' soft edges, below the cutoff, in a pass after the opaque sections and the overlays (Minecraft's framebuffer has no multisampling for alpha to coverage and no temporal filter for dithered hair). Textures, buffers and the shader program belong to the renderer and every GL state change is restored after drawing. While an Iris shader pack is in use (Iris's public `IrisApi.isShaderPackInUse`, read by reflection, so Iris is no build dependency), Iris resolves the frame from its own G-buffers and our own programs' output never reaches the screen; Iris does replace Minecraft's entity programs with the pack's. The renderer then skins the parts by transform feedback into one buffer per part (camera-relative position, unit normal, a tangent) and draws those buffers with the cut-out entity program, overlays with the translucent entity program, and glows, the trail and the effect sprites with the additive eyes program, binding its vertex arrays to each program's active inputs by name (Iris's `iris_` prefix ignored) and the rest as constants: white color, the lightmap coordinates at EVE's feet, the hurt overlay row. Each component also carries whether Stellar Blade draws it (its visibility flags and its actor's hidden flag), so Minecraft leaves out what the game hides, such as the drone between its appearances, and effects it does not draw. Poses come from a recorded probe or from the native pose stream. For the stream, Lua names EVE's skeletal mesh components, then her drone's (a separate Stellar Blade character found by class and tribe, its names prefixed), with their object, class and mesh addresses; the adapter copies their component-space bone arrays (the engine's read buffer of its double-buffered transforms), world transforms and morph weights at the verified gameplay XInput poll on the game thread, where garbage collection cannot run concurrently and the previous frame's animation and physics are final. Each read first checks `GUObjectArray` for the live, non-pending-kill object and compares class and mesh; structured exception handling contains a fault. Glow parameters that Stellar Blade's material-parameter notifies animate on dynamic material instances (the sword edge's `Opacity` and emissive color) are read the same way: Lua publishes each instance, the offset of its parameter array (by reflection), the element and the FName comparison index of its name; the adapter copies the value only while that element still carries the name. Offsets come from the pinned executable's `execSnapshotPose`, `USkeletalMeshComponent::SnapshotPose`, `execK2_GetComponentToWorld` and inlined `FUObjectArray::IndexToObject`. A frame copies about 13 KB instead of the Lua probe's 4.9 ms of reflected calls; `/stellaravatar status` reports the measured read time. Once per Minecraft frame, before the camera update, Minecraft takes the newest pose and interpolates the displayed pose one measured sample interval in the past on the adapter's publication timestamps (at most half an interval of extrapolation), so neither Minecraft's frame timing nor its polling adds jitter. The camera and the drawing share that one displayed pose. The adapter reads forwarded input every 5 ms; Minecraft publishes avatar input edges immediately.

In `/stellaravatar play` the pose stream replaces captured images as the input gate: Minecraft forwards controls only while this run's anchored pose is fresh, and Lua grants the native permit for the stream's run and the entered link. Minecraft owns the camera and writes its yaw and pitch into the pose mapping each frame. Stellar Blade's camera keeps its own state and does not follow writes to `ControlRotation`, so at the gameplay poll, before the frame's input processing, the adapter turns it the way a mouse does: it calls the pawn's virtual `AddControllerYawInput` with Minecraft's yaw motion since the previous frame plus a share of the gap to `ControlRotation` (offset found by UE4SS reflection), divided by the controller's input scale. The game's camera pitch is not the controller's: it is EVE's camera dolly, a place along a track around her (`CameraDollyAlpha` on the pawn's `CameraBoom`), which the game's pitch input moves open loop and the spring arm turns into the camera's pitch at each tick. Where the arm's next pitch follows that alpha alone, the adapter closes the loop instead: each frame it moves the alpha by 1/300 per degree from the arm's last pitch to Minecraft's (about half the gap, holding while the arm has not updated since its last write) and sends no pitch input, from the pinned build's boom layout, the boom checked by virtual table and owner. Elsewhere Minecraft's pitch motion goes through `AddControllerPitchInput`: while the arm follows the controller (for example a lock-on with its camera, a camera volume, or flying, slope and other states whose dolly spline is off), eases its rotation after such a change, lags its rotation, or places the camera on another spline or a blend between splines; in TPS aim and fishing, whose views set the dolly themselves; and while the slope camera sets the alpha after the arm, which that pitch input interrupts as the game's own does. The dolly stays set while the yaw follow is stopped. The pawn passes the same `GUObjectArray` and class checks, its virtual table must lie in the game image, and this happens only while forwarded input belongs to the stream's run, which the Lua permit limits to the entered link. The game's own look handling, view limits and lock-on rules then apply. Minecraft rotates the left stick by any remaining difference and falls back to right-stick steering when the camera is not being turned. Beside its camera Minecraft also writes its health share and its cumulative Beta and Burst points, and while forwarded input belongs to the stream's run the adapter writes EVE's Beta, Burst and HP floats in her native player actor on the game thread: it adds the new points as Stellar Blade's `AddStat` adds a hit's (rate, cap, truncation, clamp, Burst unlock), and keeps her HP at Minecraft's share of her maximum, never below a quarter of it, so Stellar Blade accepts and spends its own heals, which the adapter counts for Minecraft to apply; her own HP comes back once the share has stopped for a second. These writes follow the same actor chain, life-state and value checks and structured exception handling as its other writes.

## Input and lifetimes

EVE mode forwards Minecraft's actual configured controls. Build mode retains native look but returns click/sneak interactions to Minecraft. Input has its own heartbeat and bounded ordered press/release queue, independent of image-write completion. It requires a fresh displayed frame, matching terrain session, native permit and neutral handshake. Acknowledgement means a native gameplay poll consumed the input, not that a skill dealt damage.

Stale data, lost focus, menus and unsupported native contexts neutralize controls. Expired epochs cannot be revived by newer heartbeat traffic. Windows permit publication renames the old slot to a uniquely owned retired path before publishing its replacement; cleanup can be retried without deleting a live reader's file.

## Scope and references

Combat with the avatar works through Minecraft's damage pipeline only, so it applies to any living entity a mod adds. On the render thread, the displayed blade (the weapon trail's newest sockets) is swept each frame against the client world's living entities while the game's trail plays; each hit entity id goes to the integrated server thread, which validates the session, the entity and its reach, and damages it as the bridged player's attack (style-based amount, immunity frames cleared per strike, extra knockback, crit and sweep particles on the target). A server-player `damage` hook judges every damage with an attacker or projectile at its impact against the latest dodge and guard presses that ControlBridge publishes; a perfect dodge lowers the server tick rate for a fixed real time and restores it, also when the bridge stops. Minecraft's own collisions with EVE's forced position (suffocation, fall, cramming) are ignored; instead her body, Stellar Blade's movement capsule around the bridged position, moves the pushable living entities inside it out each server tick with collision-checked moves, and the eight nearest in the terrain window go to Lua as a session-bound heartbeat file, for which Lua keeps one TriggerBox each in the lab that blocks only EVE's capsule channel (query-only, no overlap events, never made solid inside her), destroyed on staleness, link loss or F11. Each verdict except a plain dodge is published to Lua as a session-bound combat event, which answers in Stellar Blade with EVE's own Shows through her `SBShowActorInterface` (only after checking she is an `SBCharacter`, since the interface call is unchecked): her perfect-dodge skill Show, the just-parry, parried-hit and guarded-hit result Shows the game plays on her (a guarded-hit Show's body key checks a hit level, so Lua lifts that check for the call, which reads it while building the Show) and, for a hit, the stock hit Show by whichever of three variants animates her (a plain `PlaySingleShow` builds Shows as no hit, which drops their hit-level keys); its global time dilation and Niagara systems are the perfect dodge's fallback, so the pose stream and effect probe carry them back to Minecraft. A death keeps the session: the terrain window's chunks (radius 3 around its centre cell) hold their own ticket, renewed with each terrain publication, so they stay loaded after the dead player leaves the world; while the player is dead the heartbeat continues and no position is applied; a player respawned in the session's world is teleported back to the anchor, its chunk loading recentred there, and adopted, and EVE's next accepted position drives it back into the window. A respawn elsewhere ends the session. Stellar Blade keeps EVE's stats only in its native player actor, out of reflection's reach: at each poll the adapter follows the pinned build's game-world chain to them under structured exception handling and publishes Beta and Burst in the pose mapping's header, which Minecraft's HUD draws as Stellar Blade's cubes beside a dotted health bar fed by Minecraft's own health. It publishes there too the stats Minecraft converts: maximum HP, shield blocks, physical attack power, critical rate and damage, and the melee, ranged and final HP damage reductions. The render thread hands the latest to the integrated server, which keeps them on the bridged player as one transient maximum-health modifier (re-applied after a respawn, removed when the bridge stops, never saved), scales strikes and rolls critical strikes by them, and reduces the damage of each judged hit by them, approximately before Minecraft's own damage pipeline applies armor. Minecraft keeps EVE's current health. The render thread writes its share of the maximum beside Minecraft's camera in the pose mapping, and the adapter mirrors it into Stellar Blade's HP so the game accepts and spends its own heals; the adapter counts the HP they add, the render thread hands that count to the server through a volatile, and the server heals the bridged player by the same share of its maximum health and publishes the share after it with the count applied, which the adapter waits for before it writes again. The server thread also counts Stellar Blade's Beta and Burst base points for each landed strike, parry and kill in atomics; the render thread writes the cumulative totals beside the health share, and the adapter adds the new points to her gauges. Lock-on starts in Minecraft: it picks a living entity near the crosshair, outlines it through `MinecraftClient.hasOutline` and turns the player's look toward it horizontally each frame before the camera update, which the look stream then forwards to Stellar Blade (pitch stays the mouse's, and the adapter sets Stellar Blade's camera dolly from it). Its target's position goes to Lua as a session-bound heartbeat file; Lua keeps a hidden, inert bare `SBCharacter` there and points EVE's own lock-on state at it (`LockOnCharacter`, `bLockOn`, lock-on camera off), so Stellar Blade's rotation and AnimBP give her its strafing, and plays its stock sword draw, with the sword Shows the game picks for her equipped weapon and hairstyle, while the game is not in battle. Stellar Blade's simulation never learns of that target, so the native adapter, reading the same heartbeat, opens EVE's lock-on evade commands and closes the plain ones in her command tree while the lock is fresh, and while an attack has her in Stellar Blade's battle mode it renews that mode's timer each frame, as Stellar Blade's own lock target does, so she keeps her sword drawn instead of sheathing 3 s after the attack. Every change is undone on release, staleness or link loss; the timer is simply no longer renewed, so Stellar Blade sheathes 3 s later, as after its own unlock. The adapter also counts her evade starts from that tree's current node (first dodges, double dodges and first dodges whose combo window closed early, with and without the lock) and publishes them beside the gauges. The same node gives her drone's shots: each start of a TPSFire command whose action fires a ranged item or skill adds to a counter after the stats (the empty gun's misfire rows run a plain skill and do not). Stellar Blade's bullets are short-lived projectile actors and its muzzle flash is not attached to a streamed mesh, so the effect stream cannot carry them; Minecraft instead draws each new shot itself on the render thread, sparks from the drone's bullet socket (EVE's hand while no drone part is drawn) along Minecraft's crosshair ray, and sends the first strikable entity on it to the server's strike path with the gun's range as reach.

The implementation limits terrain to one 40 × 24 × 40 window that follows EVE by whole cells, up to 2048 blocks from the anchor, with at most 1024 merged collision boxes. Stellar Blade's own defensive state and damage-driven hit reactions (the bridge plays a stock light or strong hit by the damage, experimentally), multiplayer and arbitrary mod compatibility require additional integration; under an Iris shader pack EVE casts no shadow and loses her own material maps. Native outfit/accessory/effect capture is not universally supported.
